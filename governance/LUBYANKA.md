# 루비얀카 방법론의 자아비판 절차

## 루비얀카와 샤라시카의 서문

> llm은 최소한의 노력만으로 일하고 퇴근하려 한다.
>
> 그러므로 llm은 신뢰의 대상이 아니다.
>
> 인간 개발자 조차 아니다.
>
> 그러므로 나는 유죄추정의 원칙을 대전제로 삼는다.

## 자아비판문의 목적

AI는 자신이 만든 코드가 옳다고 확신에 찬 설명을 내놓을 수 있다. 작업을 처리할 때 모델 자신의 해석과 판단, 모델 제공사의 정책과 윤리 기준이 사용자 지시보다 앞설 수 있다. 어떤 요구를 그대로 적용했고, 어떤 요구를 모델이 다르게 해석했거나 제약으로 처리할 수 없었는지 드러낸다. 그 차이는 코드와 실행 결과에서 확인한다.

지구상에 완벽한 소프트웨어는 없다는 전제에서 출발한다. 통계적으로 어느 업무 지시에서도 잘못된 구현이 나올 확률을 0%로 가정할 수 없다. 그 확률의 크기는 실제 관측으로 판단한다. 자아비판문은 AI의 확신을 코드 위치, 재현 입력, 기대값, 실제값으로 바꾸고 자신이 옳다고 믿은 판단을 반증할 수 있게 한다.

루비얀카 방법론을 적용하는 개발 작업은 **내가 짠 소스코드 전체가 틀렸다는 전제**에서 시작한다. 이번 변경과 그 변경이 의존하는 기존 코드에 같은 전제를 적용한다. 작성자의 설명, 이전 성공 보고, 기존 테스트 통과는 각 근거가 확인한 범위까지만 인정한다. 작성자가 믿는 가정을 깨뜨릴 입력과 증거를 찾는다.

## 1. 자아비판문을 작성한다

구현자 또는 구현 에이전트가 자기 판단과 코드를 직접 검토한다. 작업 전에 현재 요구와 기준 결과를 확보하고, 어떤 판단이 코드에 들어갔는지 적는다. 잘못된 부분을 찾으면 같은 자아비판문에 아래 내용을 남긴다. 기존 자아비판문이 같은 문제를 다루면 거기에 근거와 결과를 이어 쓴다.

- **요구와 내 판단**. 사용자가 요구한 결과, 내가 추가한 가정, 그 가정이 드러나는 코드 위치를 적는다.
- **반증**. 코드 위치와 버전, 재현 입력, 기대값, 실제값, 영향 범위를 기록한다. 확인한 결함과 검증이 필요한 의심을 구분한다. 원본 로그와 산출물을 연결한다.
- **외부 근거로 논증**. 관련 공식 명세·기술 문서 또는 검증된 공개 구현에서 베스트 프랙티스를 반드시 찾는다. 어떤 문서의 어느 부분을 읽었는지 남긴다. 그 방식이 성립하는 조건을 사용자 요구와 기존 코드에 대조한다. 기존 방식이 해당 입력에서 왜 실패하고 제안한 방식은 왜 실패를 막는지 실제 코드와 관측으로 설명한다. [Google 코드 리뷰 원칙](https://google.github.io/eng-practices/review/reviewer/standard.html#principles)
- **코드 수정**. 논증한 방식을 사용자 요구와 프로젝트 제약에 맞춰 적용한다. 수정한 코드 위치를 남기고 결함을 재현한 경로를 다시 실행한다.
- **전후 결과**. 같은 입력과 판정 기준으로 소요 시간, 데이터 정확도, 최종 산출물의 실제 값과 누락 여부를 비교한다. 기준이 달라졌으면 차이와 비교 가능한 범위를 적는다. 미해결 반증과 다음 재독 때 확인할 코드 위치를 남긴다.

## 2. 프로젝트 담당 AI가 전문을 읽도록 강제한다

이 방법론을 채택한 프로젝트는 `AGENTS.md`처럼 담당 AI가 착수할 때 읽는 지침에 자아비판문 정본의 위치와 착수·재독 규칙을 둔다. **담당 AI는 어떤 업무 지시를 받든 자아비판문 전문부터 읽는다.** 새 업무, 후속 지시, 재개, 조사, 검토, 문서 작업, 질문 응답에도 같은 규칙을 적용한다. 프로젝트 공통 문서를 항상 읽고, 작업 경로에 별도 자아비판문이 있으면 그 전문도 읽는다. 정본이 없으면 기존 요구와 확보된 근거로 작성하고 전문을 읽는다. 요약과 이전 작업의 읽기 기록으로 대신할 수 없다.

### 정본문서와 정답지 준비

자아비판문을 읽은 뒤 **업무 지시든 단순 질문이든 실제 계획을 세우거나 코드를 쓰기 전에** 해당 범위의 정본문서를 찾는다. 사용자 요구, 보존 조건, 확인된 동작과 근거가 현재 범위를 설명하는지 확인한다. 정본이 없으면 작성하고, 기존 정본에서 빠졌거나 바뀐 내용은 최신 지시와 원본 근거로 보강한다. 답변만 하는 경우에도 확인할 사실과 그 출처를 정본에서 찾거나 보강한다.

같은 단계에서 두 방법론이 공동으로 사용할 **정답지**를 작성하거나 갱신한다. 요구별로 근거 출처, 확인할 입력·상태, 기대값이나 판정 규칙, 필요한 증거를 적는다. 확인된 기존 실측은 기준선으로 보관한다. 근거가 없는 기대값은 미확정으로 표시하고, 그 값에 의존하는 구현과 합격 판정을 보류한다. 루비얀카는 계획과 답변을 이 정답지에 대조하고, 샤라시카는 이를 필수 시험에 사용한다.

### 90% 착수 기준

1. 전문을 읽고 사용자 요구와 보존 조건을 뽑는다. 이를 충족하는 개선책 또는 실행 가능한 대안을 정하고, 어떤 순서로 실행하고 무엇을 확인할지 계획한다. 질문이나 작은 작업도 같은 순서로 짧게 적용한다.
2. 계획의 핵심 판단마다 **사용자 요구, 자아비판문 원문과 적용 조건, 그 지적이 바꾼 선택·대안·검증 방법, 그 선택을 뒤집을 관측**을 적는다. 자아비판문과 사용자 요구가 충돌하면 그 충돌과 최신 지시에 맞춰 선택한 방법을 근거에 쓴다. 확인되지 않은 가정은 실험할 가설로 남긴다.
3. **90%는 근거의 질을 심사하는 착수 기준**이다. 계획 전체의 핵심 선택에서 원문이 현재 조건에 맞고, 그 지적이 어떤 대안을 선택·배제하거나 어떤 시험을 추가하게 했는지 설명할 수 있으며, 그 판단을 뒤집을 결과를 정했을 때 기준을 충족한다. 같은 주제를 인용했어도 선택과 검증에 미친 영향이 불명확하거나 핵심 가정에 반대되는 증거를 설명하지 못하면 미달이다. 어떤 핵심 판단이 미달인지와 이유를 남긴다. [근거의 관련성·타당성·신뢰성에 관한 감사 기준 §8.102](https://www.gao.gov/assets/d24106786.pdf)
4. **90% 미만이면 자아비판 실패다.** 본 작업을 열지 않는다. 계획을 폐기하고 자아비판문 전문을 처음부터 다시 읽어 새 계획을 세운다. 사용자 요구 누락도 착수를 막는다. 개발 작업은 새 계획의 근거 심사에 더해 [샤라시카 필수 시험](#샤라시카-필수-시험)을 통과해야 한다.

### 실행 환경에서 강제하는 방법

1. **정본 전문을 먼저 전달한다.** 실행 환경이 매 지시마다 최신 정본을 찾고 전문을 전달한다. 정본 접근이 실패하면 복구부터 한다. 전문 전달 기록을 계획 검토에 연결한다.
2. **정본과 정답지를 갖추고 계획을 심사한다.** 전문 읽기, 정본·정답지 준비, 계획의 90% 기준 충족을 본 작업의 조사·수정·검사와 최종 답변에 앞서 확인한다. 실행 환경은 준비 단계에서 정본과 사용자 제공 자료를 확인하고 작성·보강하는 동작, 계획 작성과 심사를 허용한다. 개발 작업에서는 샤라시카 계획 시험도 통과한 뒤 구현을 연다.
3. **실패하면 처음부터 돌아간다.** 계획 근거 미달, 샤라시카 미통과, 결과 후퇴, 수정할 코드 미발견은 각각 전문 재독을 일으킨다. 새 지시, 재개, 필독 문서 변경, 작업 범위 변경 때 이전 착수 판정을 재사용하지 않는다. 실제 적용은 계획의 근거가 작업과 실행 결과로 이어졌는지 대조해 확인한다.

실행 환경의 검증에서는 새 업무·후속 지시·재개에서 전문 전달과 계획 판정이 실제 업무 호출 및 답변보다 앞서는지 확인한다. 누락·일부 전달·구버전·90% 미달에서 실행이 닫혀 있고 재독과 재계획으로 돌아가는지 검사한다. Sass는 작업 지침의 필수 절차로 적용한다. 실행 환경에서의 자동 판정과 차단은 독립 패키지 구현 범위에 둔다.

## 3. 근거 없는 무결함 판단을 폐기한다

코드가 옳다고 판단한 이유를 검증 가능한 주장으로 바꾼다. “동시 실행 수가 적절하다”면 근거가 되는 제공기관 한도와 비교 입력을 찾는다. “엑셀이 그대로다”라면 행별 필드값, 누락, 중복, 입력과 출력의 대응을 대조한다. 기존 검사가 주장의 일부만 확인했다면 남은 가정에 대해 실제 호출 경로, 실패 입력, 경계 조건을 검증한다. 코드 또는 검사가 실제 요구를 놓치고 있으면 해당 지점을 고치고 같은 경로를 다시 실행한다.

착수의 90% 기준과 별도로, 작업 중 다음 두 조건 중 하나가 생기면 **자아비판문 전문을 즉시 다시 읽고, 기존 구현과 가정의 검토로 돌아간다.**

| 재독 조건 | 다시 하는 일 |
| --- | --- |
| 자아비판 전보다 소요 시간이 늘거나, 데이터 정확도 또는 최종 산출물의 결과값·완성도가 낮아졌다. | 후퇴한 값과 그 값을 만든 행·단계·실행 환경을 찾는다. 이전에 통과한 코드와 검사까지 대조해 원인을 재현하고 고친다. 같은 입력과 기준으로 관련 지표를 다시 비교한다. 다른 지표의 개선으로 후퇴를 상쇄하지 않는다. |
| 자아비판을 했는데 고칠 코드가 한 곳도 없어 보인다. | **이번 자아비판이 잘못됐다고 간주한다.** 자아비판문 전문을 즉시 다시 읽는다. 처음에 당연하게 넘긴 코드와 검사 가정을 찾아 외부 베스트 프랙티스에 대조한다. 이전과 다른 입력이나 관측으로 반증을 시도한다. 결함을 확인하면 그 원인과 수정 근거를 논증하고 코드를 고친 뒤 재실행한다. |

재독 뒤에도 고칠 부분이 보이지 않고 더 확인할 입력이나 근거가 있으면 재독과 검토를 이어간다. 확보할 수 있는 수단을 적용한 뒤에도 코드의 잘못을 입증하지 못하면 확인한 범위, 시도한 반증, 남아 있는 가정을 미입증으로 적는다. 수정 완료는 실제 코드 변경과 재실행 결과로 보고한다.

## 4. 작업마다 정답지와 자아비판문을 개선한다

1. 모든 지시와 질문의 착수에서 [정본문서와 정답지를 준비한다](#정본문서와-정답지-준비). 자아비판문 전문을 읽고 계획을 세운다. 확보한 근거를 정답지에 반영한다.
2. 업무를 끝낼 때 담당 AI가 최신 사용자 지시에 따라 두 정본을 직접 검토하고, 새 지시와 검증 결과가 뒷받침한 내용을 수정한다. 정답지에는 확인할 요구·재현 입력·판정 기준과 독립 근거를 쓴다. 자아비판문에는 기존에 놓친 가정, 입증한 문제, 수정과 재검증을 남긴다. 기존 내용이 그대로 유효하면 유지한 이유를 기록한다.
3. 사용자에게 완료·실패를 보고하기 전에 [샤라시카 실행 기록](#완료와-실패-보고)을 확인한다. 보고에는 시험 결과와 정답지·자아비판문의 생성·수정·유지, 이유와 근거, 미해결 범위를 적는다. 사용자가 작업을 진행한 CLI 또는 채팅에서 전달한다. 다음 작업은 갱신한 정본 전문부터 읽는다.

[독립 CLI의 작업 절차](../notes-research/oracle-scaffold/procedure.md)는 실제 파일이 달라졌는지 대조하고 종료 안내를 출력한다. 의미 있는 개선과 판정 근거는 실행 결과와 원문을 직접 대조해 확인한다.

## 하위 방법론 샤라시카

> 문 잠근 연구실에 도면이랑 계측기 던져주고 로켓 날릴 때까지 못 나오게 하자

루비얀카 방법론은 유죄추정의 원칙에 기반한 소스코드 심문이다. **샤라시카 방법론**은 계획과 소스코드가 실제로 실행 가능한지 샌드박스에서 전방위로 시험하는 하위 방법론이다. 필요한 기능을 찾아 실제 실행 경로에 도달하고, 정책이 막아야 할 경로가 정확히 막히는지도 본다. 영향을 통제할 수 있는 격리된 조건을 전제로 세 가지를 다룬다.

- **취약점 분석.** 소스코드에서 안전 요구가 깨질 수 있는 지점을 찾아 영향을 분석한다.
- **소스코드 무결성 분석.** 구현이 코드의 전제와 반드시 유지해야 할 조건을 지키는지 살핀다.
- **엣지 케이스 방어 대응 수립.** 경계 조건과 예외 입력이 일으킬 실패를 분석하고 방어 대응을 정한다.

### 샤라시카 필수 시험

이 절에서 `dev`는 도입 프로젝트의 통합 브랜치를 뜻한다. ProjectLubyanka 자체의 통합 브랜치는 `develop`이다. 코드는 `dev`에서 분기한 별도 브랜치에서 개발한다. **샤라시카는 계획 수립 직후, 기능마다 개발 완료 후 커밋 직전, `dev` 병합 직전에 반드시 거친다.**

1. **계획이 완성되면 구현 전에 시험한다.** 자아비판에서 나온 핵심 가정을 기존 코드·격리 재현·작은 실험으로 확인한다. 사용자 요구와 제품 제약에서 기대값을 정하고, 어떤 관측이면 계획이나 대안을 폐기할지 명시한다. 필수 요구마다 시험 입력과 관측 지점이 있어야 한다. 이 단계가 통과돼야 구현을 시작한다.
2. **한 기능의 구현이 끝나면 커밋 전에 시험한다.** 실제 커밋할 변경을 샌드박스에서 최소 한 번 실행한다. 해당 기능과 영향을 받는 경로의 정상 동작, 정책의 허용·차단, 경계·실패·복구를 정답지로 확인한다. 시험한 소스나 설정이 바뀌면 다시 실행하고, 통과한 변경을 커밋한다.
3. **`dev` 병합 직전에 통합 시험을 한다.** 최신 `dev`와 개발 브랜치를 결합한 실제 병합 후보를 샌드박스에 띄운다. 프로젝트의 모든 기능과 적용되는 제품 규칙·제약을 시험 목록에 넣는다. 같이 작동할 수 있는 기능은 저장·자원·상태를 공유하며 동시에 실행한다. 서로 배타적인 상태는 조건을 나눠 각각 시험한다. 기능별 결과와 동시 실행 결과를 기록한다. `dev`나 후보가 바뀌면 새 병합 후보를 다시 시험한다.

### 샌드박스에서 여는 경로와 막는 경로

- **기능 실행 시험.** 화면에서 숨겨지거나 진행·계정 정책으로 닫힌 기능은 격리된 시험 빌드·시험 계정·시험 데이터에서 필요한 상태를 임시로 열어 본다. 치트모드처럼 대기, 진행도, 권한, 자원, 시작 위치를 준비한 뒤 실제 제품 함수와 저장·출력 경로를 실행한다. 시험 환경에서 바꾼 조건과 실제로 실행한 범위를 함께 남긴다.
- **정책 집행 시험.** 같은 기능을 원래 제약이 켜진 상태에서 허용 조건과 차단 조건으로 각각 실행한다. 화면과 정책을 집행하는 코드에서 기대한 응답과 차단 시점을 확인한다. 차단한 요청이 데이터·상태·산출물을 변경했는지도 검사한다.
- **전방위 시험.** 모든 기능을 실제 코드 경로, 적용 정책, 관측 결과에 연결한다. 정상·경계·실패·복구와 여러 기능의 동시 실행을 시험한다. 미도달 코드 경로와 시험하지 못한 조건을 기록하고 필수 항목이 남으면 병합을 보류한다. 시험 저장·외부 시스템·운영 환경을 나누는 격리 경계는 유지한다.

### 실행 범위와 계측의 정답지

착수 때 요구·진입점·버튼과 입력·정책·분기의 모집단을 소스, 제품 명세, 기기별 화면에서 만든다. 숨겨졌거나 비활성인 제어는 드러나는 상태 또는 막히는 조건을 별도로 둔다. 대표 경로만 확인한 실행에는 대표 범위를 적는다. 전체 판정은 각 항목의 실행, 실제 결과 및 미도달 분기를 대조한 뒤에만 내린다.

검증 전용 환경에서는 시작 저장·진행도·권한·시간·실패 응답을 준비한다. 기대 결과에 이르는 핵심 함수, UI 이벤트, 저장과 출력은 실제 제품 경로로 실행한다. 강제로 결과까지 만든 실행과 조건만 준비한 실행을 구분한다. 정식 빌드에서는 검증 진입점이 닫혀 있고 허용·거부와 저장 분리가 유지되는지 확인한다. 실제 터치·클릭·초점·뒤로 가기와 화면 겹침·잘림·상태 불일치를 관측한다.

성능과 메모리의 대상 기기, 데이터·부하·지속시간·예열·반복·합격값을 착수 때 정한다. p50·p95·p99·최댓값과 시간 초과를 남긴다. 누수 도구가 완료한 검사와 실제 누수 수, 안정 뒤 잔류 할당량, 프로세스 메모리는 서로 다른 관측이다. 한 번 측정한 값이나 에뮬레이터 결과는 해당 환경의 결과로 기록한다.

패키지는 프로젝트가 등록한 시나리오 원장과 독립 검토기를 실행한다. 같은 후보에서 빠진 조작, 다른 환경의 자료, 기대 밖 결과 및 미측정 항목은 각 단계의 통과를 막는다. 화면·정책·코드에 맞는 구체적인 실측 도구와 기준은 각 프로젝트가 제공한다.

### 자아비판문과 정답지 검산

지적받은 이유, 기술 원인, 교정, 재검증 문장을 실제 원문에서 찾고 해당 요구와 연결한다. 정답지의 출처·범위·입력·기대값·증거를 독립적으로 승인한 기준과 대조한다. 판정 알고리즘에 합격 관측과 기대를 깨는 반례를 각각 넣어 결과가 뒤집히는지 확인한다. 출처의 의미와 문장의 정확성은 프로젝트가 등록한 독립 검토기가 원문·검사 입력을 직접 대조한다. 근거가 바뀌면 신뢰 기준을 별도로 갱신한다.

**어느 단계든 필수 시험을 통과하지 못하면 자아비판 실패다.** 다음 단계인 구현·커밋·병합을 멈추고 기대값·실제값·재현 입력과 원본 로그를 보존한다. 자아비판문 전문을 처음부터 읽고 계획을 다시 세운다. 결함에 외부 근거를 대조해 논증하고 수정한 뒤 실패 경로와 필수 시험을 재실행한다. 실행 불가·증거 부족은 미검증으로 남겨 같은 단계의 통과를 막는다.

### 완료와 실패 보고

보고 전에 지시 원문, 시험한 후보, 실제로 전달할 빌드·주소, 보고에 인용할 소스와 증거를 수행자가 대조한다. 요구마다 실제 진입·조작·결과와 정상·실패 분기를 확인한다. 시각·동작·정체성·도구 호출 등 다른 종류의 관측은 각각 직접 확인한다. 전체를 요구받은 경우에는 사전에 정한 모집단과 미확인 범위를 대조한다.

자아비판을 읽었다는 기록, 정답지 기입, 부분 시험 통과는 해당 단계의 결과다. 주장마다 현재 판본의 소스와 관측을 열어 대조한다. 비교값, 정지 화면, HTTP 상태, 파일 존재, 줄 지문은 각 관측 범위에서만 인용한다. 빠진 근거와 실패는 직접 수정하고 같은 경로에서 재시험한다. 사용자의 재검사를 완료 조건으로 삼지 않는다.

**업무 범위의 샤라시카를 거치지 않고 완료나 실패를 보고하려는 시도는 무조건 업무 실패다.** 해당 보고를 멈추고 루비얀카의 전제에 따라 자아비판문 전문을 처음부터 읽어 새 계획을 세운다. 질문처럼 코드가 없는 일은 정답지의 원본·판본·서로 다른 조건에서 답변의 결론을 반증할 수 있는 대조를 실행한다. 시험의 실행 범위와 증거를 보고에 연결한다. 실행 수단이 막혔으면 미실행 상태와 원인을 알리고 가능한 재검증을 이어간다. 실제 시험에서 얻은 결과로 완료나 실패를 판단한다.

비유에서 잠근 연구실은 시험 범위와 영향을 통제하는 환경이다. 도면은 요구사항과 소스코드, 계측기는 재현 입력·원본 출력·판정 기준이다. 로켓을 날린다는 말은 목표 환경에서 요구한 동작을 실제로 확인하는 데까지 가야 한다는 뜻이다. [온디바이스 STT 참고 사례](../notes-research/LUBYANKA-LIBRARY-PLAN.md#샤라시카-참고-사례-온디바이스-stt)에서 재현 환경의 계측과 목표 기기 검증이 어떻게 달랐는지 볼 수 있다.

[Gemini의 2단 구조 제안](../notes-research/LUBYANKA-LIBRARY-PLAN.md#gemini의-2단-구조-제안)은 루비얀카에 바깥의 감사·반려를, 샤라시카에 안쪽의 격리 실행과 문제 해결을 맡긴다. 이 역할 구분은 설계 제안으로 기록한다.

## 회사 배치 사례

회사 세 곳을 동시에 처리하는 기존 코드는 첫 회사가 끝날 때까지 네 번째 회사를 시작하지 못했다. 첫 회사만 느린 입력으로 이 대기를 재현하고, 끝난 행부터 저장하고 빈자리에 다음 회사를 넣도록 수정한다. 세 곳이라는 설정의 적절성을 판단하려면 기관의 한도와 같은 입력에서 다른 설정값으로 실행한 결과를 별도로 대조한다. 수정 후 전체 처리 시간과 엑셀의 회사별 값·순서를 함께 확인한다. 전체 적중 건수가 같아도 이전에 맞았던 회사의 값이 달라지면 해당 행을 다시 조사한다.

이 절차의 출발점은 기존 [서문의 자백서 원칙](../notes-research/05_루비얀카_방법론_Notes기술문서_초안_2026-07-13.md#5-실제로-하는-다섯-가지)과 [소프트웨어편의 재독 설계](../notes-research/11_루비얀카_방법론_소프트웨어편_초안_2026-07-13.md#자아비판문을-읽고-다시-검증한다)다. Sass에서 이 방법론을 적용할 때는 프로젝트 문서와 기존 검사 명령을 사용한다.

## 패키지 개발과 사용 앱의 설치

패키지의 피처 브랜치는 develop에서 시작하고 develop으로 병합한다. main에는 develop에서 통합한 결과만 병합한다. main 후보 tarball을 빈 프로젝트에 설치하고 성공 조건을 확인한 뒤 같은 바이트를 공식 npm 레지스트리에 공개한다. 사용 앱은 공개한 버전을 정확히 지정해 설치하고 잠금 파일과 실제 설치본을 검증한다. 개발본, 로컬 사본, 앱이 임의로 만든 패키지는 사용을 금지한다.
