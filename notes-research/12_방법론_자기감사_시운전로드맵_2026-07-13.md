# 루비얀카 방법론 자기감사 — 무는 것 vs 그려진 문 + 시운전 로드맵 (Document 12)

> 도입: 2026-07-13
> 목적: 루비얀카 방법론을 **그 자신의 기준으로 취조**한다 — 우리가 처방한 기제 중 실제로 *무는* 것과, 아직 *그려진 문(theater)*인 것을 가른다. 그리고 미검증 항목의 **시운전 우선순위**를 세운다.
> 계기: 사용자가 ADR이 강제 안 되는 걸 실측 확인 + "기록하고 계속 보게 한다"는 하네스 절대원칙도 체감상 반쪽만 산다고 지적. 이론편이 "자기감시는 썩는다"고 했으니, 방법론이 자기 theater를 스스로 나열하는 것 자체가 방법론이 작동하는 증거다.
> 근거: 8프로젝트 실측(Phase1 + 수집) + 카논/훅 그렙.

---

## §1. 이미 무는 것 (시운전 완료·실전 검증)

| 기제 | 왜 무는가 |
|---|---|
| pre-commit/pre-push 차단(시크릿·tsc·빌드·e2e-smoke) | 안 통과하면 실제로 커밋/푸시 불가(tier D) |
| 도구제한 검증 에이전트(qa=Edit/Write 없음) | 구현자·검증자 구조적 분리(지시 아님) |
| docs-sync 바이트 대조(`diff -q`/SHA256) | "같다"는 말 안 믿고 바이트로 확인 |
| main 인간 전용 · `--no-verify` 금지 | 프로덕션 문은 인간만 |
| 메모리쓰기 훅(Stop/PreCompact) | 커밋했는데 메모리 없으면 경고/차단 |
| 완료어구 스킬 · 결정론 센서(verdict+exit) | 완료 선언이 검증을 강제 발화 |

→ **git 게이트 층 + 구조적 에이전트 제한 = 방법론의 검증된 뼈대.**

## §2. 아직 안 무는 것 (그려진 문 후보 — 처방됐으나 미검증/미가동/실패)

중요도 순. 각 항목: 왜 실패하나 → 고치는 방향.

**🔴 1. 독립 레드팀(패키지 ②)** — *가장 큰 미검증.*
설계만 있고 실물 0. 게다가 **프로젝트 안의 레드팀은 이미 썩었다**(Doc1: 안 돎). 방법론의 간판 주장이 실전에서 부재.
→ 고침: 외부 CI 서비스로 실제 구축(§3·Doc6). 단 최대 난이도, 별도 트랙.

**🔴 2. 자기진화(발견 학습 + 연구·파울러 반영)** — *이미 실패한 적 있다.*
Grimoire판이 30일 자율호출 0회로 아카이브. "돈다"가 아니라 "안 돌아 치웠다."
→ 고침: 되살리기 전에 *왜 지난번 죽었는지*부터. 화이트리스트+사람승인 게이트는 유지하되, 자율 트리거가 아니라 사람이 당길 때만 도는 on-demand로 재설계.

**🔴 3. "기록하고 계속 보게 한다"(하네스 책 절대원칙)** — *반쪽만 산다.*
사용자 체감 확인: 자백은 기록되는데(incident-log 커짐), **일 많으면 안 본다.** 뿌리: **쓰기=tier D(훅 강제) / 재독=tier A(기억해서 읽어야).** tier A는 바쁘면 무조건 무너진다.
→ 고침(tractable): **재독을 tier D로 내린다 — incident가 세션을 *찾아오게* 한다.** 세션 시작 시 미해결 자백을 컨텍스트 주입 / 관련 영역 건드리기 전 해당 자백을 강제 대면. "기억해서 찾아 읽기" → "그게 너를 막아선다."

**🟡 4. ADR 강제** — 0/8(tier A). 단 **셋 중 제일 쉽다**(결정론적 발자국 게이트).
→ 고침: 발자국(deps·스키마·설정·구조·아키텍처 문서) 건드린 커밋은 `docs/decisions/` 항목 없으면 차단. advisory→튜닝→차단.

**🟡 5. 스캐폴드 `lubyanka init`** — 설계만, 미구현.
→ 고침: 공통 골격(Doc10) 자동 생성. 구조=자동, SSOT=인간.

**🟡 6. 다른-벤더 교차검증(원칙 5)** — 강의엔 있는데 **어느 프로젝트에도 배선 0.** 잘해야 수동 습관.
→ 고침: 검증 단계에 다른 모델 호출을 실제 배선(비용 계층 주의).

**🟢 7. 측정조건 검증("측정 장비도 거짓말")** — 한 번 잡았지(‑O0), 상시 게이트 아님(일회성 교훈).
→ 고침: 벤치마크 전 빌드 플래그 결정론 체크를 게이트화.

**🟢 8. verifier 상시 가동** — grimoire-verifier는 태어났지만 *루틴 가동*은 미확인(휴면 가능).
→ 고침: 배포 전 필수 단계로 배선 + 가동 로그 확인.

**정직한 헤드라인:** ADR은 미검증이지만 *쉬운 축*. 진짜 무서운 건 **1(레드팀: 간판인데 실물 0)·2(자기진화: 이미 실패)·3(재독: 절대원칙인데 반쪽)** — 문서엔 있는데 실전엔 없거나 죽었다.

## §3. 왜 레드팀은 프로젝트 밖에 있어야 하나 (사용자 정본 + 정직한 벼림)

**사용자 정본(2026-07-13):** 루비얀카 패키지와 레드팀 패키지를 나누는 이유 — 레드팀이 프로젝트 안에 있으면 안 된다. **프로젝트를 모르고, 자신만의 절대 룰에 기반해, 프로젝트를 만진 세션·에이전트·하네스가 예측 못 하는 방식으로 공격해야** 검증이 된다.

**정직한 벼림 한 가지:** *완전한 무지*는 효과적 공격을 못 한다(무엇을 때릴지 모름). 작동하는 실현형은 —
> **구현·하네스·자기정당화엔 눈감되(blind), 외부 계약(무엇을 해야 하는가=spec/공개 API)과 보편 룰(OWASP·불변식·property)엔 밝다.**

즉 레드팀은 **빌더의 *이야기*(프로젝트가 자기를 어떻게 설명하는지)를 안 읽고, 외부 기준으로 판정한다.** 이것이 "프로젝트를 모른다"의 정확한 실현 — 그래야 상관 맹점(같은 Claude면 같은 사각)을 깨면서도 헛방이 아니다. 이 원리가 곧 §2-1 레드팀의 설계 사양이다(Doc4 §3·Doc6 §3 정합).

## §4. 시운전 로드맵 (우선순위)

**원칙: 쉬운·tractable부터 실물을 붙여, 매 항목 "실제로 하나 잡았다"를 눈으로 확인.** ("게이트 존재"는 성공이 아니다 — honesty-audit 기준.)

1. **ADR 발자국 게이트**(§2-4) — 결정론적, FunnelPage 확장 가능. *단 지금 당장은 무리(사용자 판단) — 워크트리·최신·튜닝 준비되면.*
2. **재독 강제**(§2-3) — 절대원칙 복원. incident가 세션을 찾아오게(세션시작 주입). tractable.
3. **측정조건 체크**(§2-7) · **verifier 루틴 배선**(§2-8) — 좁고 명확.
4. **스캐폴드 init**(§2-5) — 공통 골격 자동화.
5. **다른-벤더 교차검증 배선**(§2-6) — 비용 주의.
6. **자기진화 재설계**(§2-2) — 왜 죽었는지부터. on-demand.
7. **독립 레드팀 구축**(§2-1) — 최대 난이도, 외부 서비스, 별도 트랙.

각 항목 공통 성공 기준: **미검증/미기록/미공격 사례 하나를 실제로 잡아 강제했고, 그걸 확인함.**
