# 루비얀카 문서 정본 체계와 타 프로젝트 이식 계획

**계획안 · 2026-11-28.** 개발자가 정한 목적을 최상위 기획 정본에 고정한다. 코드 규칙, 인프라, 하위 방법론은 그 목적을 각 영역에서 실현하는 방법을 정한다. 도입 프로젝트에서는 AI가 요구를 줄이거나 필수 시험을 생략했을 때 **어느 단계가 어떤 근거로 작업을 막았는지** 재현할 수 있어야 한다. 이 문서의 제안이 정본으로 채택되기 전까지 [현행 방법론](../governance/LUBYANKA.md)을 따른다.

## 1. 문서의 위계와 결정권

정본은 특정 범위에서 결정을 내릴 때 참조하는, 개발자가 효력을 부여한 문서다. 같은 규칙의 원문은 한 곳에 둔다. 다른 문서에는 그 규칙의 위치와 해당 영역에서 수행할 일을 적는다.

| 위계 | 결정할 내용 | 작성·변경 원칙 |
| --- | --- | --- |
| 개발자의 명시적 지시와 원문 | 목적, 우선순위, 보존 조건, 요구의 변경·철회 | 최초 원문과 후속 정정을 각각 보존한다. 최신 명시적 정정은 해당 범위에 적용한다. AI의 추정으로 미언급 요구까지 폐기할 수 없다. |
| 최상위 기획 정본 | 설립 목적, 적용 대상, 필수 절차와 모듈, 공용 패키지와 도입 프로젝트의 책임, 성공 기준 | 제안 경로는 `governance/PROJECT-CHARTER.md`다. 기존 정본과 개발자 원문에서 조항을 옮겨 근거를 붙인다. 새 의무·예외·범위 변경은 개발자가 결정한다. |
| 분야별 정본 | 코드 규칙은 구현·호환성 범위를, 인프라 문서는 Git·CI·배포 권한을, 방법론 문서는 착수·반증·필수 시험·종료 절차를 정한다. | 각 문서에 상위 조항, 담당 범위, 변경 권한, 확인 방법을 명시한다. 현재 방법론 정본을 절차의 기준으로 활용한다. 샤라시카와 추가될 필수 모듈은 루비얀카가 정한 범위 안에서 자체 절차를 정의한다. |
| 프로젝트별 상세 명세와 실행 기준 | 실제 진입점, 제품별 정책·기기·환경, 코드 검사, 입력·기대값·증거 | 도입 프로젝트가 자기 기획 정본에 맞춰 작성한다. 제품 조건을 구체화하거나 검사를 추가할 수 있다. 공용 필수 단계의 삭제나 공용 통과 기준의 완화는 패키지 변경 요청으로 올린다. |

**예시.** 개발자가 “사용 앱은 공식 npm 공개본만 설치한다”고 정하면 최상위 기획에 이를 보존 조건으로 둔다. 인프라 문서는 정확한 버전·잠금 파일·공식 배포 파일·설치 파일을 대조하는 방법을 정한다. 바사리는 자신의 npm 루트와 검증 명령을 정할 수 있다. 로컬 tgz를 허용하는 바사리 문구가 발견되면 충돌 위치를 기록하고 도입 판정을 보류한다. 반대로 바사리의 캡션 검사가 강화돼도 공용 패키지에 캡션 규칙을 넣을 이유는 없다. [설치 출처 검사](../verification/endpoint-install.mjs) · [바사리 사건 기록](../verification/vasari-report-audit.md)

## 2. 기존 자료를 보존하며 정본을 세우는 순서

1. **현재 문서의 역할부터 조사한다.** 루트 README와 AGENTS는 진입 안내, `governance/LUBYANKA.md`는 현행 절차, `lubyanka-oracle.json`은 판정 기준, 자아비판문은 실패·재검증 이력으로 분류한다. `notes-research/`의 원전·기획안·배포용 설명서와 `verification/`의 실측은 각각 출처·상태를 표시한다. 파일 목록, 상충 문구, 옮길 상위 조항을 먼저 제출한다. 역사적 문장에서 당시 판본과 맥락을 지우지 않는다. [연구 색인](README.md) · [기존 구현 계획](LUBYANKA-SHARASHKA-IMPLEMENTATION-PLAN.md)
2. **최상위 기획과 정본 목록을 작성한다.** 조항마다 근거 원문·판본과 적용 범위를 연결한다. 목록에는 문서 ID, 정본 경로, 담당 범위, 상위 조항, 상태(초안·유효·대체됨), 대체한 판본을 둔다. 사람이 읽는 원문에서 실행 설정을 대조할 수 있게 하고, 배포물에는 해당 버전의 방법론·필수 모듈 목록·절차를 동봉한다. README, AGENTS, 호스트별 진입 문서는 같은 정본을 가리키게 한다.
3. **새 하위 방법론의 원문을 인수한다.** 파일이면 받은 바이트를, 채팅이면 전달받은 텍스트와 메시지 순서를 보존한다. 분할 원문은 순번별로 두고 정정본도 따로 남긴다. 원문·정리본·채택 조항을 연결해 역추적할 수 있게 한다. 현재는 원문 대기 상태다. 명칭, 역할, 샤라시카와의 선후관계, 입력, 출력, 실패 조건은 원문을 받은 뒤 정한다. 필수 모듈로 채택한 버전부터 모듈 누락 시 다음 단계로 진행할 수 없게 한다.
4. **상위 지침의 침범과 충돌을 판정한다.** 기계 검사는 상위 조항 누락, 순환 참조, 같은 범위의 유효 정본 중복, 필수 모듈 누락, 판본 불일치를 찾는다. 의미 검토는 원문과 하위 조항을 나란히 두고 의무 약화, 금지의 허용, 범위 축소, 다른 분야 권한 변경 여부를 판정한다. 하위의 명백한 오기는 상위에 맞게 고친다. 동급 정본의 모순이나 상위 지시의 상충으로 해석에 따라 결과가 달라지면 두 원문과 영향을 개발자에게 올린다. 충돌에 의존하는 작업만 보류한다.
5. **변경을 아래로 전파한다.** 상위 조항을 정식 변경하면 연결된 하위 문서·정답지·필수 모듈·도입 프로젝트 검사를 찾아 재심사한다. 변경 전 합격 기록은 기존 판본의 이력으로 보존하고 새 판정에는 새 후보의 증거를 요구한다. 코드 변경자가 같은 변경에서 상위 기준과 검토기를 바꿔 스스로 승인할 수 없게 한다.

## 3. 다른 프로젝트에서 절차를 강제하는 지점

기존의 `adopt`, `begin`, `plan`, `permit`, `verify`, `review-draft`, `finish` 및 Git 훅을 출발점으로 삼는다. 자아비판 기록에서는 기존 ID가 전부 있어도 새 사용자 요구가 사라졌고, 검사 CLI의 성공을 실제 호스트의 차단으로 확대해 보고했다. 그래서 아래 시험은 **등록된 요구 하나를 빼는 경우와 새 요구를 등록하지 않은 경우**, **CLI 호출과 실제 호스트 조작**을 각각 다룬다. [관리 CLI](oracle-scaffold/managed.md) · [설립·적용 진단](../verification/diagnosis-2026-11-28.md)

| 시점 | 실행 주체와 검사 | 허용 또는 반려를 입증할 관측 |
| --- | --- | --- |
| 새 지시·질문·재개 | 호스트가 사용자 원문, 공용 패키지 판본, 프로젝트 기획·해당 분야 정본·자아비판문 전문·정답지를 준비한다. 준비용 읽기와 계획 수정을 허용한다. | 필독 문서가 없거나 오래됐을 때 구현 도구가 닫힌다. 최신 자료로 다시 시작하면 정상 계획을 제출할 수 있다. |
| 계획에서 구현으로 | 독립 검토기가 원문의 각 요구·보존 조건을 상위 조항, 결정, 실제 시험, 그 결정을 뒤집을 관측과 대조한다. 개발 작업은 샤라시카 계획 시험 뒤 작업 허가를 발급한다. | 원문 구절 누락과, 구절을 모두 복사하고도 관계없는 시험을 붙인 계획을 각각 기각한다. 새 요구에 맞는 시험을 추가한 계획은 허용한다. |
| 기능 커밋·통합 | 스테이징한 기능 후보와 최신 통합 브랜치를 합친 후보를 각각 격리 시험한다. 로컬 Git 훅이 참조 갱신을 검사한다. 원격 필수 검사는 서버가 병합할 바로 그 후보를 독립적으로 검사한다. | 시험 후 파일 또는 통합 기준이 달라지면 이전 합격으로 커밋·병합할 수 없다. 훅 없는 별도 복제본에서 올린 미검증 변경도 원격에서 거부돼야 원격 강제로 기록한다. |
| 완료·실패 보고 | 원본 관측을 후보·동선·주장에 연결한다. 호스트는 실제 전송할 답변을 검토하고 승인된 내용과 일치할 때 전달한다. 질문은 정본과 반례 대조를 실행한다. | 정지 화면으로 동작 전체를 주장하거나 승인 뒤 문장을 추가한 보고를 차단한다. 실패를 재현하고 제한을 입증한 보고, 직접 교정하고 같은 경로를 재시험한 보고는 해당 범위로 전달한다. |
| 실패·범위 변경 | 이전 허가를 무효화하고 원본 로그를 보존한다. 전문 재독, 재계획, 관련 시험 재실행으로 복구한다. 정답지와 자아비판문의 변경 또는 유지 이유를 기록한다. | 실패 직후 같은 내용의 새 작업을 열어 통과할 수 없다. 기준 갱신 뒤에도 기존 실패 기록과 새 관측을 각각 열 수 있다. |

**권한의 한계도 시험한다.** Codex와 Claude는 별개 호스트로 취급한다. 제안한 연결 방식은 각 호스트에서 첫 쓰기·셸 실행과 실제 답변 전송을 시험한 뒤 확정한다. 차단 기능이 없는 호스트는 통제 가능한 실행기·보고 경로에서만 승인 결과를 전달한다. 사용자가 별도 채팅이나 복제본을 사용할 수 있으면 그 경로의 차단 여부도 표시한다. 쓰기 권한이 분리된 원격 필수 검사 또는 배포 실행기가 없으면 “로컬 검사 적용”까지만 보고한다.

## 4. 이식 순서와 완료 기준

| 순서 | 담당과 산출물 | 다음 단계로 넘어갈 근거 |
| --- | --- | --- |
| 1. 생산자 저장소에서 자체 적용 | ProjectLubyanka가 문서 목록과 기획 정본, 충돌 검토기, 필수 모듈 등록·실행 계약을 준비한다. 기존 계획과 현행 절차의 중복 규칙을 대조한다. | 정상 하위 규칙은 승인한다. 부모 누락·순환·상위 금지 완화·필수 모듈 생략은 해당 조항과 함께 반려한다. 생산자 저장소 자체에서 한 작업을 착수부터 보고까지 실행한다. |
| 2. 격리된 도입 시험 | 빈 저장소와 기존 지침·훅·CI가 있는 저장소에서 설치·재설치·업그레이드를 시험한다. 기존 문서를 등록하고 설치 전후 차이를 확인한다. | 두 번째 설치가 지침을 복제하거나 기존 훅을 지우지 않는다. 갱신 실패 때 이전 공식 버전과 호환 설정으로 복구한다. 이전 시험 기록은 보존한다. |
| 3. 공용 버전 공개 | 생산자가 develop에서 분기해 통합하고 develop만 main으로 병합한다. main 후보 파일을 깨끗한 프로젝트에 설치해 정상·반례를 확인한 뒤 같은 파일을 npm에 공개한다. | 공식 레지스트리에서 정확한 버전을 새로 설치해 후보와 무결성·실제 파일을 대조한다. 이 단계가 끝나야 사용 앱으로 보낸다. [릴리스 검증](../verification/README.md) |
| 4. 첫 사용 앱인 바사리 | 바사리 전담 세션이 기존 제품 기획·코드 규칙·인프라·시나리오를 상위 조항에 연결한다. 공개 버전 고정, 잠금 파일, 실제 설치 파일, CLI 경로를 검사한다. 화면·기기별 기대값은 바사리 저장소에 둔다. | 공식 설치본 승인과 로컬 tgz·개발본·패치본 거부를 확인한다. 실제 업무 한 건에서 새 요구를 빠뜨린 계획을 먼저 반려하고 교정한 계획과 실제 제품 관측을 다시 판정한다. 공용 결함은 버전·재현·기대값·실제값을 묶어 이 전담 세션에 전달한다. |
| 5. 두 번째 환경에서 재이식 | 바사리와 다른 구조의 시험 프로젝트로 같은 공개 패키지를 가져간다. 언어별 테스트 명령, 도메인 정답지, 기기 조건은 프로젝트 설정에서 공급한다. | 공용 패키지 수정이나 바사리 전용 파일 없이 동일 절차를 실행한다. Codex·Claude, 로컬·원격, 사용자에게 전달한 보고의 결과를 따로 남긴다. |

기존 프로젝트가 더 엄격한 규칙을 갖고 있으면 보존한다. 도입 프로젝트의 기획과 공용 필수 규칙이 양립하지 않으면 충돌을 명시한 뒤 해결한다. 업데이트와 복구 모두 정식 공개본을 사용한다. 샌드박스에서 생산자가 후보를 미리 설치한 결과는 사용 앱 도입 실적으로 세지 않는다.

**판정 단위.** 각 시험 기록에 사용자 지시, 상위 조항·판본, 패키지 버전, 후보 커밋, 호스트, 입력·기대값·실제값, 허용 또는 차단된 위치, 원본 증거를 남긴다. 문서 체계, 패키지 강제, 사용 앱 도입은 위 표의 해당 근거를 확보한 범위에서 각각 완료로 판정한다. 이번 산출물은 그 시행 순서와 인수 조건을 정한 계획이다.
