# 루비얀카 문서 정본 체계와 타 프로젝트 이식 계획

**계획안 · 2026-11-28.** 이번 범위는 프로젝트의 기본 문서와 그 작성·변경 절차를 갖추는 일이다. 현재 문서의 권한과 위치는 [최상위 기획 정본](../governance/PROJECT-CHARTER.md)에서 확인한다. 3절과 4절은 문서 절차를 세운 뒤 진행할 방법론 고도화와 이식 계획이다.

## 1. 문서의 위계와 결정권

원고 대기 단계 이후 1~5번 본문과 6번의 적용 범위 설명을 접수했다. 아래 단계의 원래 기획과 연결되는 역할·충돌·구현 순서·인수 시험은 [원고 분석과 고도화 계획](METHODOLOGY-UPGRADE-PLAN.md)에 기록했다.

정본은 특정 범위에서 결정을 내릴 때 참조하는, 개발자가 효력을 부여한 문서다. 각 규칙을 변경할 정본은 하나다. 개발자 원문은 근거로 보존한다. 배포본은 해당 판본의 정본에서 만들고, 다른 문서는 정본의 위치와 해당 영역에서 수행할 일을 적는다.

| 위계 | 결정할 내용 | 작성·변경 원칙 |
| --- | --- | --- |
| 개발자의 명시적 지시 | 목적, 우선순위, 보존 조건, 요구의 변경·철회 | 최초 원문과 후속 정정을 각각 보존한다. 최신 명시적 정정은 해당 범위에 적용한다. 아이디어 메모는 제공된 상태로 보존한다. 메모에서 의무로 채택할 사항은 개발자의 명시적 지시를 근거로 삼는다. |
| 최상위 기획 정본 | 설립 목적, 적용 대상, 필수 절차와 모듈, 공용 패키지와 도입 프로젝트의 책임, 성공 기준 | 개발자 원문은 보존하고 기획 조항에서 출처를 가리킨다. 기존 분야 문서의 상위 규칙을 기획 정본으로 옮길 때는 같은 변경에서 옛 위치를 참조로 바꾼다. 새 의무·예외·범위 변경은 개발자가 결정한다. |
| 분야별 정본 | 코드 규칙은 구현·호환성 범위를, 인프라 문서는 Git·CI·배포 권한을, 방법론 문서는 착수·반증·필수 시험·종료 절차를 정한다. | 각 문서에 상위 조항, 담당 범위, 변경 권한, 확인 방법을 명시한다. 현재 방법론 정본을 절차의 기준으로 활용한다. 샤라시카와 추가될 필수 모듈은 루비얀카가 정한 범위 안에서 자체 절차를 정의한다. |
| 프로젝트별 상세 명세와 실행 기준 | 실제 진입점, 제품별 정책·기기·환경, 코드 검사, 입력·기대값·증거 | 도입 프로젝트가 자기 기획 정본에 맞춰 작성한다. 제품 조건을 구체화하거나 검사를 추가할 수 있다. 공용 필수 단계의 삭제나 공용 통과 기준의 완화는 패키지 변경 요청으로 올린다. |

**예시.** 개발자가 “사용 앱은 공식 npm 공개본만 설치한다”고 정하면 최상위 기획에 이를 보존 조건으로 둔다. 인프라 문서는 정확한 버전·잠금 파일·공식 배포 파일·설치 파일을 대조하는 방법을 정한다. 바사리는 자신의 npm 루트와 검증 명령을 정할 수 있다. 로컬 tgz를 허용하는 바사리 문구가 발견되면 충돌 위치를 기록하고 도입 판정을 보류한다. 반대로 바사리의 캡션 검사가 강화돼도 공용 패키지에 캡션 규칙을 넣을 이유는 없다. ## 2. 기존 자료를 보존하며 정본을 세우는 순서

1. **현재 문서의 역할부터 조사한다.** 루트 README와 AGENTS는 진입 안내, `governance/LUBYANKA.md`는 현행 절차, `lubyanka-oracle.json`은 판정 기준, 자아비판문은 실패·재검증 이력으로 분류한다. 이관한 원전 8건과 Sass 기준 커밋에 남은 6건, 후속 개발자 정정을 함께 조사한다. `notes-research/`의 기획안·배포용 설명서와 `verification/`의 실측은 각각 출처·상태를 표시한다. 파일 목록, 상충 문구, 옮길 상위 조항을 먼저 제출한다. [연구 색인](README.md) · [원전 위치와 설립 이력](../verification/diagnosis-2026-11-28.md)
2. **최상위 기획과 정본 목록을 작성한다.** 조항마다 근거 원문·판본과 적용 범위를 연결한다. 목록에는 문서 ID, 정본 경로, 담당 범위, 상위 조항, 상태(초안·유효·대체됨), 대체한 판본을 둔다. 사람이 읽는 원문에서 실행 설정을 대조할 수 있게 하고, 배포물에는 해당 버전의 방법론·필수 모듈 목록·절차를 동봉한다. README, AGENTS, 호스트별 진입 문서는 같은 정본을 가리키게 한다.
3. **새 하위 방법론의 원문을 인수한다.** 루비얀카 산하 필수 모듈이라는 지위는 개발자가 정했다. 현재는 원문 대기 상태다. 파일이면 받은 바이트를, 채팅이면 전달받은 텍스트와 메시지 순서를 보존한다. 분할 원문과 후속 정정을 각각 남기고 정리본·채택 조항에서 출처를 가리킨다. 명칭, 역할, 샤라시카와의 선후관계, 입력·출력·실패 조건은 원문을 받은 뒤 확정한다. 위계 조사와 기존 절차 검증은 지금 진행할 수 있다. 새 모듈을 포함하는 판본은 명세와 실행 증거를 갖춰야 공개할 수 있다. 그 판본에서 모듈이 누락되면 적용 단계의 통과를 막는다.
4. **상위 지침의 침범과 충돌을 판정한다.** 상위 조항 누락, 순환 참조, 필수 모듈 누락, 판본 불일치를 검사한다. 같은 파일에 코드 규칙과 배포 규칙이 함께 적용될 수 있다. 같은 판본·적용 범위에서 같은 결정을 내릴 권한을 두 정본에 주면 중복으로 반려한다. 조항 ID가 달라도 실제 의무가 겹치는지는 원문을 대조한다. 하위 조항이 상위 의무를 약화하거나 금지를 풀면 상위를 적용하고 하위를 고친다. 최신 명시적 지시로도 해소할 수 없는 충돌은 두 원문과 영향을 개발자에게 올린다. 독립된 작업은 진행할 수 있다. 원래 요청의 필수 조건에 충돌이 남으면 그 요청의 완료 판정은 보류한다.
5. **변경을 아래로 전파한다.** 상위 조항을 정식 변경하면 연결된 하위 문서·정답지·필수 모듈·도입 프로젝트 검사를 찾아 재심사한다. 변경 전 합격 기록은 기존 판본의 이력으로 보존하고 새 판정에는 새 후보의 증거를 요구한다. 코드 변경자가 같은 변경에서 상위 기준과 검토기를 바꿔 스스로 승인할 수 없게 한다.

## 3. 다른 프로젝트에서 절차를 강제하는 지점

기존의 `adopt`, `begin`, `plan`, `permit`, `verify`, `review-draft`, `finish` 및 Git 훅을 출발점으로 삼는다. 자아비판 기록에서는 기존 ID가 전부 있어도 새 사용자 요구가 사라졌고, 검사 CLI의 성공을 실제 호스트의 차단으로 확대해 보고했다. 그래서 아래 시험은 **등록된 요구 하나를 빼는 경우와 새 요구를 등록하지 않은 경우**, **CLI 호출과 실제 호스트 조작**을 각각 다룬다. [관리 CLI](oracle-scaffold/managed.md) · [설립·적용 진단](../verification/diagnosis-2026-11-28.md)

| 시점 | 실행 주체와 검사 | 허용 또는 반려를 입증할 관측 |
| --- | --- | --- |
| 새 지시·질문·재개 | 공통·해당 경로의 자아비판문과 방법론 정본 전문을 읽고, 사용자 원문·패키지 판본·해당 분야 정본·정답지를 확인한다. 첫 도입이나 지시 변경 때는 근거가 있는 정본·정답지의 작성·보강·재독을 허용한다. | 빈 저장소에서 준비 문서를 작성할 수 있다. 준비와 계획 심사를 마칠 때까지 본 작업과 최종 답변은 보류한다. 준비 권한으로 제품 파일을 수정하는 시도는 거부한다. |
| 계획에서 실행으로 | 독립 검토기가 각 요구·보존 조건을 결정, 실제 시험, 그 결정을 뒤집을 관측과 대조한다. 현행 정본의 90% 착수 기준은 근거의 질에 적용한다. 개발 작업은 샤라시카 계획 시험을 통과한 뒤 허가한다. | 요구 하나를 빠뜨린 계획과 구절만 복사해 관계없는 시험을 붙인 계획을 각각 기각한다. 질문도 해당 정본과 정답지로 반례를 대조한 뒤 답한다. |
| 기능 커밋·통합 | 스테이징한 기능 후보와 최신 통합 브랜치를 합친 후보를 각각 격리 시험한다. 로컬 Git 훅이 참조 갱신을 검사한다. 원격 필수 검사는 서버가 병합할 바로 그 후보를 독립적으로 검사한다. | 시험 후 파일 또는 통합 기준이 달라지면 이전 합격으로 커밋·병합할 수 없다. 훅 없는 별도 복제본에서 올린 미검증 변경도 원격에서 거부돼야 원격 강제로 기록한다. |
| 완료·실패 보고 | 원본 관측을 후보·동선·주장에 연결한다. 호스트는 실제 전송할 답변을 검토하고 승인된 내용과 일치할 때 전달한다. 재현한 실패를 고칠 수 있으면 직접 교정하고 같은 경로를 다시 시험한다. | 정지 화면으로 동작 전체를 주장하거나 승인 뒤 문장을 추가한 보고를 차단한다. 시험 수단이 막히면 미실행 항목과 원인을 전달하고 가능한 검증을 이어간다. 필수 시험이 남은 작업의 종료는 보류한다. |
| 재독·재계획 | 계획 근거 미달, 필수 시험 미통과·미실행, 결과 후퇴, 코드 검토에서 고칠 곳을 못 찾은 경우 전문을 다시 읽고 핵심 가정을 재검토한다. 새 지시·재개·필독 문서 또는 범위 변경 때도 이전 허가를 재사용할 수 없다. | 시험이 녹색이어도 같은 입력에서 소요 시간이 늘면 재독한다. 같은 요청을 다시 열어 실패를 지울 수 없다. 원본 로그와 후속 반증·교정·재시험을 연결하고 정답지와 자아비판문의 변경 또는 유지 이유를 남긴다. |

**권한의 한계도 시험한다.** Codex와 Claude 각각에서 첫 제품 파일 쓰기·셸 실행·실제 답변 전송을 시험한다. 관리 실행기에서 차단돼도 일반 채팅이나 다른 복제본에서 그대로 진행되면 두 결과를 함께 기록하고 호스트 전체 강제 판정은 보류한다. 로컬 훅, 원격 병합, npm 공개도 각각 차단을 관측한 경로만 인정한다.

패키지의 브랜치 생성 시험은 `main`과 `develop`이 서로 다른 커밋일 때와 같은 커밋일 때 모두 실행한다. 두 경우 모두 `develop`에서 시작한 작업만 허용해야 한다. 현재 훅은 두 브랜치가 같은 커밋이면 `main`을 지정한 생성도 허용했다. 브랜치를 만드는 시점에 어느 브랜치를 지정했는지 확인하고 직접 생성 경로에서도 금지를 입증해야 이 항목을 통과시킨다. ## 4. 고도화 이후의 이식 순서

현재 사용 앱은 바사리아트워크 하나다. 패키지는 `develop`에서 검증한 결과를 `main`에 병합한다. 배포 절차는 아래 3단계에서, 바사리의 실제 설치·제품 검증은 공개 후 4단계에서 확인한다.

| 순서 | 담당과 산출물 | 다음 단계로 넘어갈 근거 |
| --- | --- | --- |
| 1. 생산자 저장소에서 자체 적용 | ProjectLubyanka가 기획 정본과 문서 목록을 기준으로 충돌 검토기, 모듈 등록·실행 절차의 후보를 준비한다. 개발자 지시와 검토 전 확정한 기대값으로 후보를 심사한다. | 서로 다른 의무를 정한 하위 문서는 같은 경로에 적용해도 승인한다. 상위 참조 누락·순환·상위 금지 완화·해당 판본의 필수 모듈 생략은 반려한다. 생산자 저장소에서 한 작업을 착수부터 보고까지 실행한다. |
| 2. 생산자의 격리 시험 | 생산자가 만든 임시 시험 저장소 두 곳에 공개 전 후보를 설치한다. 하나는 비워 두고 다른 하나에는 기존 지침·훅·CI를 둔다. 이전 공개본에서 후보로 갱신하는 경우도 시험한다. | 다시 설치해도 지침은 한 번만 들어가고 기존 훅은 작동해야 한다. 갱신 실패를 재현해서 설치본·설정·잠금 파일 복구와 이전 기록 보존을 확인한다. 복구한 버전이 현재 적용할 필수 조건을 충족할 때만 작업을 재개한다. |
| 3. 공용 버전 공개 | 피처는 `develop`에서 분기해 `develop`에 병합한다. `main`에는 `develop`만 병합한다. 원격에 반영한 `main`에서 후보 파일을 한 번 만들고 빈 시험 프로젝트에 설치해 정상·반례를 실행한다. | 공개 직전에 시험이 통과했고 `main`·`develop`과 파일 해시가 검증 때와 같은지 확인한다. 하나라도 다르면 공개를 멈춘다. 모두 맞으면 그 파일을 npm에 공개한다. 공개를 릴리스로 기록하고, 공식 버전을 새로 설치해 후보와 무결성·실제 파일이 일치한 뒤 사용 앱에 전달한다. [릴리스 검증](../verification/README.md) |
| 4. 첫 사용 앱인 바사리 | 바사리 전담 세션이 기존 제품 기획·코드 규칙·인프라·시나리오를 상위 조항에 연결한다. 화면·기기별 기대값은 바사리 저장소에 둔다. | 바사리의 공식 설치본을 검증한다. 실제 업무 한 건에서 새 요구를 빠뜨린 계획을 먼저 반려하고 교정한 계획과 실제 제품 관측을 다시 판정한다. 공용 변경 요청·결함은 건마다 버전·재현·기대값·실제값과 함께 ProjectLubyanka 전담 세션에 전달한다. |

다른 프로젝트가 실제로 도입할 때는 같은 공식 패키지에 그 프로젝트의 테스트 명령·정답지·기기 조건을 연결한다. 그 프로젝트의 도입 여부는 이번 패키지 공개 조건에 포함하지 않는다.

바사리를 포함한 사용 앱은 최초 설치·갱신·복구 모두 공식 npm의 정확한 공개 버전을 사용한다. 로컬·개발·임의 제작본을 사용 앱에 설치해서 시험하는 경로도 금지한다. 바사리에서는 설치 명세·잠금 파일의 로컬 참조와 기존 개발 사본을 제거하고 공식 버전으로 다시 설치한 뒤 실제 파일과 CLI 경로를 대조한다. 로컬본 거부 반례는 생산자의 임시 시험 저장소에서 실행하거나 앱에 이미 남아 있는 위반을 검사해 확보한다.

복구 뒤에는 현재 공용 필수 규칙과 제품별 검사를 다시 실행한다. 구버전에서 필수 검사가 빠지면 그 검사에 의존하는 작업은 보류한다. 기존 프로젝트의 더 엄격한 규칙은 보존하고, 공용 지침과 충돌하는 변경 요청은 ProjectLubyanka에 전달한다. 바사리의 전달 기준은 바사리 저장소 `analysis/docs/LUBYANKA-CONTRACT.md`의 ‘공용 패키지 변경 전달’을 따른다.

**판정 단위.** 각 시험 기록에 사용자 지시, 상위 조항·판본, 패키지 버전, 후보 커밋, 호스트, 입력·기대값·실제값, 허용 또는 차단된 위치, 원본 증거를 남긴다. 문서 체계, 패키지 강제, 사용 앱 도입은 위 표의 해당 근거를 확보한 범위에서 각각 완료로 판정한다. 이번 산출물은 그 시행 순서와 인수 조건을 정한 계획이다.
