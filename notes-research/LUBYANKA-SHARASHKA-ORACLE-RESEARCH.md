# 루비얀카·샤라시카의 정답지 전제와 판정 기준 연구

## 전제가 성립하는 범위

**두 방법론은 완료를 판정할 근거를 요구한다. 모든 프로젝트에 사전에 완성된 유일한 정답지가 있다는 전제는 성립 범위가 좁다.** 출력이 하나로 정해지는 기능은 기대값을 만들 수 있다. 허용 결과가 여러 개인 기능은 허용 범위나 반드시 지킬 조건을 검사한다. 최신 외부 사실, 청취 품질, 주관적 디자인처럼 자료나 사람이 필요한 판정은 확보한 범위까지만 내린다. 기술 문헌은 주어진 입력과 관측에서 올바른 동작을 구별하는 이 문제를 **테스트 오라클 문제**라고 부른다. [Barr 등, 테스트 오라클 문제 연구](https://discovery.ucl.ac.uk/id/eprint/1471263/1/06963470.pdf)

방법론의 전제는 **결과를 통과시키려면 그 결과를 만든 구현과 별도로 근거를 세워야 한다**로 정리한다. 여기서 ‘정답지’는 기대값, 판정 규칙, 판정 범위와 출처를 함께 뜻한다. 합격 기준이 모호하면 기준을 명확히 하거나 필요한 자료를 확보한다. 전체를 판정할 근거가 없더라도 확인 가능한 조건에서 실패를 찾고, 어떤 결과가 미판정인지 남긴다.

| 구분 | 질문 | 예 |
| --- | --- | --- |
| 요구 및 판정 기준 | 어떤 결과를 받아들일 수 있는가 | 같은 요청을 다시 보내도 저장 행이 하나여야 한다. |
| 참조 자료 | 기대값의 근거는 어디에서 왔는가 | 사용자 원문, 공식 계약, 사람이 교정한 전사, 동일 조건의 원작 실행 기록. |
| 기준선 | 이전에 같은 조건에서 무엇을 관측했는가 | 직전 빌드의 프레임 분포, 기존 엑셀의 행별 오답. 이전 실패도 기준선에 남긴다. |
| 실제 관측 | 이번 후보에서 무엇이 일어났는가 | 화면과 버튼 결과, DB 재조회, 저장 파일, 원본 오디오와 전사, 프레임 trace. |

기준선과 정답지를 분리해야 후퇴와 기존 결함을 모두 잡을 수 있다. 예를 들어 전후 적중이 모두 90곳이어도 기존에 맞던 한 행이 틀려졌으면 그 행은 후퇴다. 반대로 기준선부터 틀렸던 행을 후보가 바르게 출력하면 독립 근거로 확인해 개선으로 기록한다.

## 사용자 명령에서 판정 기준을 만든다

1. **원문에서 요구와 보존 조건을 뽑는다.** 사용자 명령의 해당 구절을 요구 ID에 연결한다. 해야 할 일, 유지해야 할 동작, 실패할 때의 기대 결과를 분리한다. 현재 코드에서 본 결과는 구현 관측으로 붙인다.
2. **다른 사람이 같은 조건으로 재실행할 수 있게 적는다.** 시작 상태, 입력, 실제 실행 경로와 관측 지점, 기대값이나 허용 조건, 판정 단위·분모를 적는다. 명령에 없는 값은 공인 계약에서 가져올 수 있는지 확인한다. 결과 선택이 달라지는 모호한 부분은 결정할 항목으로 올리고, 이미 명확한 조건부터 진행한다.
3. **말을 실행 가능한 판정기로 옮긴다.** 정확히 같은 값, 허용 집합·범위, 상태 변화, 전후 관계, 사람이 보는 기준표 중 맞는 것을 고른다. 자연어 해석을 보조하는 모델은 원문 근거와 해석을 함께 제시한다. 형식이 정해진 규칙은 문서에서 판정기를 만들 수 있다. Javadoc의 예외 설명에서 자동 판정을 만든 연구도 예외 조건이라는 한정 범위에 적용됐다. [Goffi 등, 예외 동작의 오라클 자동 생성](https://star.inf.usi.ch/media/papers/2016-issta-goffi-toradocu.pdf)
4. **판정기 자체도 시험한다.** 맞는 입력·출력을 통과시키고, 틀린 결과·비어 있는 결과·판정에 필요한 원본이 없는 경우를 구별하는지 본다. 바뀐 코드가 실제로 실행됐어도 결과를 하나도 확인하지 않았다면 요구의 검증 범위는 늘지 않는다. [Schuler와 Zeller, 코드 실행과 결과 검사의 차이](https://www.st.cs.uni-saarland.de/publications/files/schuler-stvr-2013.pdf)

**실제 지시의 변환 예.** ProjectSendPrLetterAddr는 전체 원본 행에서 99% 이상 적중해야 한다. 적중은 대상 회사의 사업자등록번호·정식 법인명·대표 발송주소·우편번호·대표 전화 다섯 개가 최신 독립 근거와 모두 맞는 한 결과다. 120행이면 119행이 필요하다. 독립 근거가 부족한 행은 판정 이유를 남기고, 사용자 집계 규칙에 따라 전체 120행을 분모에 유지한다. 이 명령은 **판정 규칙**을 정한다. 실제 회사별 다섯 값은 별도 근거에서 확보한다. 당시 전수 감사에서 독립 기준표의 대표전화가 비어 있는 회사가 있었다. 해당 행은 현행 대표전화를 독립적으로 확인해야 적중에 넣을 수 있다. 근거는 `ProjectSendPrLetterAddr/AGENTS.md` §0과 서버 `docs/plans/company-match-99-20261121.md`의 120행 비교다.

## 라이브러리가 자체적으로 기준과 검사를 만드는 방법

자체 생성에는 두 동작이 있다. **이미 근거가 있는 의미를 계산하거나 검사 코드로 옮기는 일**과 **요구에 없던 기대 동작을 제안하는 일**이다. 첫 번째는 근거와 전제가 맞으면 자동화한다. 두 번째는 제안 상태로 보관하고, 사용자 요구나 독립 근거가 확인될 때 합격 기준에 반영한다.

| 근거 | 라이브러리가 만들 수 있는 판정 | 판정 범위 |
| --- | --- | --- |
| 공식 프로토콜·수식·상태표 | 스키마와 입력 범위, 참조 계산, 전이 검사, 정상·오류 사례 | 명시된 계약에 한정한다. 예를 들어 HTTP 상태 코드와 응답 형식을 검사한 뒤, 저장된 데이터나 화면에서 실제로 원하는 동작을 별도로 확인한다. |
| 사용자가 확인한 예제·독립 수집 자료 | 고정 입력과 기대 결과 표. 원본, 판본이나 조회 시점, 허용 변환을 기록한다. | 해당 샘플·원본·시점의 검증이다. 후보 앱이 방금 만든 출력에서 골든 파일을 갱신하는 일은 사용자 요구 변경이나 독립 재확인으로 처리한다. |
| 같은 계약을 따르는 독립 구현·원작 포팅판 | 동일 입력에서 결과가 갈리는 지점을 찾는 차등 검사 | 차이는 조사 단서다. 어느 쪽이 맞는지는 계약이나 원본 관측으로 판정한다. 두 구현이 같은 잘못을 공유할 수 있다. [McKeeman, 차등 테스트](https://www.cs.tufts.edu/comp/150FP/archive/bill-mckeeman/DifferentailTesting.pdf) |
| 도메인 불변식·입출력 관계 | 정답 문자열을 몰라도 확인할 성질을 테스트한다. 같은 원본 행을 재시도했을 때 중복 저장이 생기지 않는지와 같은 조건이다. | 입증한 관계만 판단한다. 유효한 전제에서 관계가 깨지면 반증이 된다. 관계를 통과해도 다른 성질의 판정은 남는다. [Chen 등, 메타모픽 테스트 원 연구](https://arxiv.org/abs/2002.12543) |
| 기존 정상판 실행 기록·성능 측정 | 고정한 기기·빌드·입력·예열·반복에서 회귀 비교와 후퇴 보고 | 이전 동작과의 일치 및 측정 조건에 한정한다. 예상 지연이나 허용 오차는 계약에서 가져온다. 새로운 이상을 숨기도록 기준선을 다시 만들지 않는다. |
| 사람이 구별할 수 있는 기준 | 음성 청취, 디자인 적합성, 서로 충돌하는 요구의 선택지를 보여주고 판정 기록을 남긴다. | 모델은 관측과 비교표를 준비한다. 취향·우선순위나 서로 다른 근거의 우열이 아직 정해지지 않으면 판정을 보류한다. |

### 프로젝트별 대조

- **웹.** “버튼이 보인다”와 “눌렀을 때 지정한 서비스가 실제로 요청을 처리하고 상태가 바뀐다”를 따로 검사한다. 화면 문구·색·위치에 승인 원본이 있으면 해당 기기와 상태를 고정해 비교한다. 다양한 배치가 허용이면 공통 요구인 내용·탐색·접근 조건을 확인한다. 선호하는 시각 결과는 사용자 검수 자료로 남긴다.
- **서버.** API 계약, 권한별 오류, 동일 요청의 재실행과 DB 상태를 연결한다. 2xx 본문, 저장, 재조회가 모두 맞는 사례와 오류 뒤 상태 보존을 분리한다. 외부 상태가 변하는 서비스는 스냅샷에서 판정 규칙을 반복하고 실제 조회에 필요한 최신성·출처는 별도 확인한다.
- **게임.** HeavyMach의 원작 실행이 증거가 되는 것은 같은 판본·저장·seed·입력에서 관측한 규칙이다. 시작 장비를 준비한 치트앱은 실제 발사·피해·저장으로 결과를 낸다. 예열한 프레임 예산과 실제 플레이의 재미는 서로 다른 판단이 필요하다. [세 게임의 치트앱 검증과 계측](SHARASHKA-GAME-VALIDATION-CASES.md)
- **녹음·STT.** ProjectSTT_OnDevice에서는 초기 네 자동 전사가 한 문장을 서로 다르게 틀렸다. 이후 turbo 전사를 초안으로 사용하되 사용자가 약 49분의 원음을 다시 듣고 교정한 316개 앵커를 만들었고, 조정용 204개와 같은 영상 후반의 별도 평가 112개를 나눴다. 초안 모델 편향이 남을 수 있고, 같은 영상 후반의 결과가 다른 화자나 음성까지 입증하지는 않는다. 화면에서 환각이 사라졌다는 판정과 모델의 환각 발생이 줄었다는 판정에는 다른 관측이 필요하다. 근거는 STT `3fad8cc`의 `research/transcription-regression-plan.md` §0·§11과 [STT 사례](LUBYANKA-LIBRARY-PLAN.md#샤라시카-참고-사례-온디바이스-stt)다.

## npm 코어에 옮길 설계와 연구 순서

1. **루비얀카가 판정 기준을 준비한다.** 기존 구현 계획의 작업 계약에 각 `requirementId`의 `source`, `scope`, `inputs`, `comparator`, `expectedOrRule`, `requiredEvidence`, `unresolved`를 연결한다. `source`에는 문서 구절·원본의 판본이나 시점·해시를 보관한다. 기존 `captureBaseline()`은 실측만 보관한다. 승인된 판정 규칙과 기준선은 각각 버전을 고정한다.
2. **샤라시카가 판정 후보를 연구한다.** 결정된 기준으로 재현하고, 빈 곳은 공식 계약에서 논리적으로 도출하거나 독립 참조·새 비교 입력을 확보한다. 작은 참조 계산을 구현할 때 제품이 사용하는 같은 함수를 호출하지 않는다. 후보 검사가 어떤 근거로 무엇을 판정하는지 함께 제출한다. 독립적으로 확인된 조건은 검증기에 연결하고, 추정과 대리 지표는 조사 기록에 둔다.
3. **검증기가 결과를 판단한다.** 고정된 후보와 판정기 버전으로 실행한다. 요구마다 `통과`, `실패`, `미판정`을 기록한다. 적용 대상 밖의 검사는 판정과 구분해 해당 없음으로 적는다. 판정 필수항목이 미판정이면 그 항목의 근거가 채워지기 전까지 전체 완료를 보류한다. 새 근거로 기준을 바꿀 때는 바뀐 이유와 범위를 남기고 같은 기준으로 이전 결과와 후보를 다시 비교한다.
4. **먼저 세 가지 작은 사례에서 검증한다.** 사용자 규칙을 식으로 옮긴 120행 합성 배치, 같은 입력을 재실행하는 서버 저장 사례, 정답 문자열 대신 보존 조건으로 확인하는 사례를 만든다. 기존 정답 한 행을 망가뜨려도 총건수가 같은 입력, 오래된 참조, 비교 기준이 빠진 입력, 참조와 후보가 같이 틀린 입력을 넣어 판정을 확인한다. 다음 단계에서 원본 접근이 허용된 게임·STT 프로젝트의 실제 증거로 반복한다.

초기 패키지의 자동 판정은 명시된 동일성·범위·불변식·전후 대조부터 시작한다. 자연어 추출과 사람이 보는 기준은 같은 요구 ID에 연결할 수 있게 설계한다. 지금 단계는 근거의 연구와 구현 제안이다. [npm 구현 계획](LUBYANKA-SHARASHKA-IMPLEMENTATION-PLAN.md)

## 첫 스캐폴드

[정답지 스캐폴드](oracle-scaffold/README.md)가 대상 폴더에 빈 판정 기준과 작성 절차를 생성한다. 사용자 원문·독립 근거, 판정 범위, 입력, 비교 규칙과 필요한 증거를 넣는다. `check`는 기입 상태와 미해결 목록을 확인한다. 실제 작동과 합격 여부는 이후 제품 실행에서 판정한다.
