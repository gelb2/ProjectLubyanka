# 루비얀카 방법론 고도화 계획

원고 6번은 1~5번을 **루비얀카 방법론 전체의 이론적 토대**로 지정한다. 루비얀카는 사용자의 의도와 보존 조건을 정의하고, 생산을 맡은 주체가 합격 조건을 바꾸거나 스스로 납품을 승인할 수 없도록 전 과정을 조직한다. 이 계획은 그 원칙을 정본, 권한, 실행 순서, 반례 시험으로 옮긴다. 기준 소스는 `develop`의 `46187aa`와 6번 원문이다. 아래의 새 모듈과 시험은 구현할 항목이다. ## 2. 현행 코드와 출발점

- `gate.mjs`의 `coversInstruction`은 검토기가 반환한 구절이 지시문 전체를 순서대로 덮는지 확인한다. `candidate`와 `receiptFor`는 시험 기록을 태스크·단계·트리에 연결한다. 이를 재사용하되 공백을 제거한 구절 비교는 무손실 원문 복원과 별도로 검증한다. `project.mjs`의 잠금과 파일 교체는 한 작업의 동시 쓰기를 다룬다. 새 원장은 여러 태스크의 순서와 장애 후 재시도를 소유해야 한다. [계획·후보 검사](oracle-scaffold/gate.mjs) · [상태 저장](oracle-scaffold/project.mjs)
- `runLab`은 지정한 Git 트리를 네트워크가 닫힌 Docker 안에서 시험한다. 현재 전달 단위는 후보 트리 전체다. 워커에 허용 파일만 전달하는 경계와 감찰용 읽기 전용 입력을 별도로 시험한다. 시나리오 계약·원본 관측·보고 영수증은 보옌프레드와 최종 보고에 연결한다. [Docker 실행](oracle-scaffold/lab.mjs) · [시나리오 판정](oracle-scaffold/sharashka.mjs) · [보고 판정](oracle-scaffold/report.mjs)
- 패키지 점검에서 설치본의 시험 0건 성공, 독립 검토기 오류 원인 누락, 생산자 저장소의 관리 설정 부재, 브랜치 출처만 검사하는 CI를 확인했다. 고도화 1차 회귀 입력으로 사용한다. 자아비판문에 기록된 바사리 캡션 누락도 유지한다. 서식·파일 개수만 맞는 경우를 잡기 위해 원문 한 구절 누락, 실측 0건, 실행되지 않은 호스트 조작을 각각 반례로 둔다. [점검 기록](../verification/package-debug-readiness.md) · [자아비판문](../LUBYANKA-SELF-CRITIQUE.md) · [CI](../.github/workflows/branch-route.yml)

## 3. 원고 간 충돌과 적용안

| 충돌 또는 빈칸 | 적용할 설계와 결정 경계 |
| --- | --- |
| 현행 정본은 매 업무 시작·실패 때 전문 재독과 수행자의 자아비판을 요구한다. 원고는 워커와 감찰에 최소 맥락을 요구한다. | 지시를 접수한 관리 계층이 전체 정본·자아비판을 읽고 계획을 대조한다. 워커에는 그 작업의 승인된 계약을 투영한다. 자아비판은 근거와 재계획에 쓰고 독립 합격 서명은 외부에 둔다. 관리 주체의 재독을 모든 자식 세션의 의무로 쓰는 기존 조항은 **구현 전 정본 개정 대상**이다. |
| 1번의 단일 함수 예, 2번의 넓은 브라운필드 맥락, 현행 샤라시카의 계획·기능·병합 3회 시험 | 쓰기 범위, 읽기 전용 인접 계약, 검증기가 실행할 전체 후보를 나눈다. 워커의 단일 파일 예가 제품 통합 검사를 줄이지 않는다. 기존 세 시점을 유지하고 기능·병합은 서로 다른 후보에 대해 다시 서명한다. |
| 2번의 자동 인수 조건 추출과 3·4번의 LLM 없는 1:1 파서 | 사용자가 번호를 매긴 최상위 항목과 그 하위 본문의 바이트 범위를 잠근다. 목록 안 예시·표·코드·인용은 소속 항목에 보존한다. 누락·중복·모호한 최상위 번호는 진단 후 착수를 막는다. 의미상 여러 목적이 한 항목에 있으면 원문을 유지하고 이견으로 기록한다. 자동 탐색기가 사용자 지시를 분할·개작할 수 없다. 원고 자체는 자유 형식 연구 자료다. |
| 3·4번의 즉시 폐기, 4번의 직전 실패 한 줄, 5번의 국소 수정과 누적 조건 | 재시도는 5번의 상세 규약을 적용한다. 단일 BUILD 오류의 기계적 진단이 사전에 허용한 유형이면 같은 전용 워크트리에서 새 원샷 세션에 1회 수정을 맡긴다. 워커 대화를 승계하지 않는다. 실패 한 줄 피드백과 다음 시도까지 보존하는 구조화 기록은 별개다. |
| 5번의 ‘3개 필드’와 예시의 4개 키, 4번의 JSON 목록 표기 | 시도 번호는 메타데이터, 나머지 세 필드는 각 한 줄로 스키마를 제안한다. 로그의 500자 이상 원문 복사와 코드 블록을 거부한다. 기존 판정문에서 세 줄의 의미를 결정론적으로 얻을 수 없으면 게이트 코드·측정값별 고정 템플릿을 사용한다. 근거가 없으면 격리한다. 원고에 붙은 목록 표식은 보존하고 실행 스키마는 별도 파일로 정의한다. |
| 4번의 직렬 배차와 선택적 OKB 병렬, 5번의 실패 횟수 | 다른 TASK-ID의 배차는 앞 태스크의 DONE까지 잠근다. OKB는 같은 시도의 독립 후보끼리만 경쟁한다. 양 게이트를 통과한 1건만 채택하고 나머지는 폐기한다. 제안은 같은 시도에서 모든 후보가 탈락했을 때 PURGED를 한 번 계수하는 것이다. 동시 합격의 우선순위와 비용 한도는 사전에 고정한다. |
| 4번의 제한된 영속 상태와 2번의 표본 검사·5번의 금지 조건·현행 증거 보존 | 작업자 컨텍스트, 시도 중 보호 기록, 종료 감사 증거를 분리한다. 사용자 영역이 원문·판본과 영수증을 보존한다. 새 워커에는 원시 실패 기록을 전달하지 않는다. DONE 뒤 보고서·이미지·반례 로그의 보관 기간과 범위는 **개발자 결정 사항**이다. 결정 전에는 기존 근거를 보존한다. |
| 2·4번의 독립 세션 대안과 5번의 3차 교차 제조사 의무 | 일반 감찰은 타 제조사가 우선이고 불가하면 동일 대화에 접근할 수 없는 독립 프로세스와 실제 제공자를 기록한다. 5번의 3차 **생산 워커** 교체는 타 제조사가 필수다. 교체에 실패하면 격리한다. 교차 검토는 숨은 의도의 정확성 자체를 보장하지 않는다. |
| 4번의 요약 상태도, 5번의 재시도 및 종료 코드 0 | 정상 흐름은 PENDING → IN_PROGRESS → VOENPRED_PASS → POLITRUK_PASS → DONE이다. 실패하면 시도에 PURGED를 기록하고 재배차하거나 QUARANTINED에서 멈춘다. 종료 코드 0은 루프가 정상적으로 멈췄다는 신호다. 제출·PR·배포는 원장 상태와 두 영수증을 읽어 격리를 거절한다. |

## 4. 계층별 계약과 실패 경로

1. **지시와 고스플란.** 사용자 영역에서 `orders.md`, `gost.json`, 해당 시각 기준의 판본을 고정한다. 고스플란이 원문 바이트 구간, TASK-ID·순서, 고정 커밋, 방법 제약, 금지 편법, 보호 경로를 원장과 카드에 연결한다. `lock/<TASK-ID>/`에는 `raw_order.txt`, `scope.json`, `protected_hashes.json`, 해당 특성화 스냅샷을 둔다. `INTENTIONAL_CONSTRAINT`와 `dissent_log`를 분리한다. 원장 쓰기와 다음 세션 배차는 한 주체만 집행한다. 잠금 실패·중복 배차·기준 HEAD 이동은 재검토한다.
2. **샤라시카 생산.** TASK-ID와 시도마다 새로운 비대화형 워커를 띄운다. 읽기 허용 파일·카드와 쓰기 허용 파일을 따로 마운트한다. 공용 Git 참조, 타 작업 디렉터리, 보옌프레드, 정답지와 보호 테스트에 대한 쓰기를 닫는다. 격리 공간에서 수정하고 시험할 수 있게 하되 검증 전에는 보호 대상 쓰기와 통합을 막는다. 작업자의 이견은 1줄로 받고 실행 불가 시 ABORT 사유를 기록한다. 워커 종료 후 후보 트리만 관리 계층에 인계한다.
3. **보옌프레드 검측.** `TAMPER → ANTI_CHEAT → BUILD/ORACLE → METRICS`에서 첫 실패로 멈춘다. 범위 밖 파일·보호 해시, skip·assertion 완화·빈 catch·승인 없는 무시 주석·프로젝트 금지 패턴, 빌드·타입·독립 시험·브라운필드 스냅샷, 해당 제품의 실측 순이다. 추가 라인 스캔과 함께 삭제·교체로 사라진 검사를 판정한다. 요구되지 않는 지표는 사전 카드에서 적용 대상 밖임을 명시한다. 필수 시험 0건·시나리오 누락·타임아웃·파싱 오류는 REJECT 및 비정상 종료다. 통과할 때만 후보 트리와 잠금 지문을 담은 `voenpred_report.json`을 발급한다.
4. **폴리트루크 감찰.** 기계 게이트를 통과한 같은 후보에 원문·압축 정본·인수 조건·diff·검증 기록·인접 타입을 전달한다. UI 작업은 실제 렌더링과 동결 기준 이미지를 함께 본다. 작성 대화·자기변호·재시도 이력은 제외한다. `politruk_verdict.json`은 PASS/NONE 또는 REJECT와 한 가지 사유(MISSING_REQ, SCOPE_SHRINK, REGRESSION, CHEAT, OVERREACH, VISUAL_DRIFT)를 갖는다. 근거는 해당 diff·증거의 위치에 연결한다. 이미지 근거는 캡처 경로·화면 좌표 또는 해당 시나리오 행으로 해석하는 계약을 제안한다. 잘못된 필드·없는 근거·주관적 디자인 반려는 합격을 만들 수 없다.
5. **폴백과 사용자 인계.** 허용한 단일 국소 BUILD 실패 외에는 시도를 폐기한다. TAMPER·ANTI_CHEAT·ORACLE·시각 이탈·월권·축소 해석과 국소 수정 재실패는 즉시 폐기한다. MISSING_REQ·REGRESSION·METRICS 등 5번의 분기표에 없는 판정은 국소 허용 목록에서 제외한다. 미등록 코드나 진단 불능은 격리하는 안을 적용한다. 실패 좌표가 없는 상태에서 재시도 조건을 꾸며내지 않는다. 시도마다 같은 기준 커밋에서 새 작업 공간을 만들고 `anti_priors.json`에 구조화 근거를 누적한다. 3회 폐기 또는 복구 자체의 실패에서 정지한다. 격리 해제는 사용자의 변경 지시와 새 판본을 근거로 기록한다.

운영 중에는 정답을 따로 보유한 정상·결함 표본으로 오탐·미탐, 격리율, 완료 시간, 모델 호출 수를 기록한다. 표본 수와 허용 오차는 바사리의 초기 분포와 비용을 측정한 뒤 정한다. 시각 작업은 기기·해상도·프레임 시간·기준 토큰을 작업 전에 고정한다. ‘60fps’ 예시 하나를 모든 앱의 합격선으로 쓰지 않는다. 의미가 불명확한 지시에서 두 모델이 같은 오답을 승인한 사례도 표본에 포함한다.

## 6. 계획 수립 중 직접 대조한 반례

- 원고 3에는 행 첫머리의 `1.`이 8번 나온다. 연구 원고를 지시 파서에 직접 넣으면 잘못된 태스크가 생긴다. 원문 보존 경로와 사용자가 작성한 `orders.md` 접수 경로를 구분해 시험한다. [3번 원문](manuscripts/originals/0003/chat.txt)
- 임시 Git 저장소에서 추적 파일을 수정해 스테이징하고 새 파일을 만들었다. `git diff --name-only`는 빈 결과였고 `git status --short`에는 두 파일이 나타났다. 기준 트리와 실제 제출 트리를 비교하고 작업 공간의 미추적·이름 변경·삭제·심볼릭 링크 경계를 검사해야 한다. [Git diff 명세](https://git-scm.com/docs/git-diff)
- 별도 임시 저장소 조건에서 `git reset --hard HEAD` 및 `git clean -fd` 뒤에도 ignore 대상 파일이 남았다. 워커가 커밋을 만들면 `HEAD`도 이미 이동해 있었다. 원장에 동결한 커밋에서 폐기 가능한 전용 공간을 다시 만들고 기준 트리·추가 파일·세션 신원을 대조한다. 실제 사용자의 작업 디렉터리는 초기화 대상에서 제외한다. 연결된 worktree는 Git 저장소를 공유하므로 권한 경계도 따로 시험한다. [Git clean](https://git-scm.com/docs/git-clean) · [Git worktree](https://git-scm.com/docs/git-worktree)
- 6번 원고를 실제로 커밋할 때 로컬 훅이 Git의 자동 `pack-refs`를 거부했다. 이후 커밋과 내용은 확인됐다. 생산자 자체 적용 시험에 참조 정리 전후의 논리적 브랜치 값 보존을 넣는다. 계획 수립 시점에 GitHub API는 `main`과 `develop` 모두 `protected: false`를 반환했다. 원격 검사는 직접 피처 병합 거부와 정상 승격 허용을 각각 관측한다. [현행 로컬 검사](../verification/branch-guard.sh) · [현행 PR 경로 검사](../.github/workflows/branch-route.yml)

계획 검토의 완료 기준은 원문별 요구·현행 코드·상충 조항·실행 반례가 연결되고 원본과 패키지 동작이 보존되는 것이다. 방법론 고도화의 완료 기준은 5절의 각 단계를 실제 후보에서 실행해 증거를 남기는 것이다.
