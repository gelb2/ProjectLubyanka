# 샤라시카 참고 사례 세 게임의 치트앱과 계측

HeavyMach 1·2와 MachDefense의 치트앱은 진행도를 올리는 시간을 건너뛰고, 필요한 상태에서 실제 게임 코드를 실행하기 위해 만들었다. 이 사례에서 **치트앱은 잠긴 연구실**, 원본 실행과 소스는 **도면**, 자동검사와 Instruments는 **계측기**에 해당한다. 정상 제품에서 기대한 동작이 실제로 일어났는지는 정식판과 목표 기기에서도 확인한다. 이는 세 프로젝트의 개발 관행을 정리한 참고 사례다. 공통 적용 시점과 통과 조건은 [샤라시카 필수 시험](../governance/LUBYANKA.md#샤라시카-필수-시험)을 따른다.

## 왜 만들었고 어떻게 개발했는가

원작 포팅판을 같은 조건의 비교 기준으로 확보한다. 원본 데이터와 실제 소비 경로에서 메뉴·무기·장비·적·미션·저장 항목을 열거한다. 복원한 로직은 공통 코어에 연결하고, 일반판과 치트판의 앱 식별자·저장 컨테이너를 분리한다. 치트판에는 원하는 스테이지·장비·레벨·자금·경험치·초기 위치를 준비할 수 있는 도구를 둔다. 상품 구입, 발사, 피해, 레벨업, 보상과 저장은 실제 게임 함수로 관측한다. 승패를 강제로 만들어 결과창이나 저장을 시험할 때는 강제 승패라는 조건을 실행 기록에 남긴다.

| 게임 | 구현과 실행 방식 |
| --- | --- |
| HeavyMach 1 | `HeavyMachValidation`/`HM_VALIDATION`으로 별도 패널과 저장을 연다. 조건을 새로 주입하는 시작과 저장을 그대로 읽는 재시작을 구분했다. `Sources/Core/ValidationScenario.cpp`는 실제 `GameData`에서 장착 가능한 플레이어 무기를 열거한다. `Sources/iOS/HMValidationPanel.mm`과 XCTest가 같은 목록과 실제 입력·게임 경로를 사용한다. 일반 앱과 치트 앱을 각각 빌드하고 배포본의 검증 진입점과 저장 분리를 확인한다. |
| HeavyMach 2 | `HeavyMach2Validation`이 `Sources/Core/Validation/ConcurrentValidation.cpp`로 독립 Session을 같은 프레임에 갱신한다. 동시에 성립할 수 있는 전투·효과·성장은 같은 전투에서 실행한다. 전투를 멈추는 메뉴나 서로 다른 저장은 별도 Session에서 실행한다. 공통 게임 코어와 실제 렌더·음향을 쓰며 실행별 저장·입력·로그·결과 파일을 분리한다. 정식판 일반 플레이까지 확인한 뒤 동일 iPad의 HD 포팅판·정식판·치트판을 마지막에 일괄 대조하도록 정했다. |
| MachDefense | 원작 호환판을 준비한 뒤 소스판의 공통 코어와 `Sources/Core/Validation/ValidationTools.cpp`의 5쪽 TEST 패널을 만들었다. 실제 게임 UI·렌더러로 그리며 미션·프로필·자금·셀·강화·특수공격·유닛을 설정한다. `Apple/Tests/MenuRenderTests.mm`과 `tools/run_apple_sweep.py`는 실제 입력·GPU·오디오·시험 저장을 연결했다. 다음 단계에서는 포팅판 대조와 원본 복원 오류 수정, 기준 커밋, 모듈 분리, 분리 전후 비교를 수행했다. |

## 프레임 기준선과 채택한 기록 방식

60Hz에서 연속 표시 콜백의 목표 간격은 약 16.67ms다. CPU 처리시간, 표시 콜백 간격, 실제 GPU 또는 표시 측정은 서로 다른 값으로 기록한다. 같은 기기·OS·빌드·저장·난수·장면·입력·예열을 기준으로 p50/p95/p99·최댓값과 기준 초과 횟수를 대조한다. 측정 중 프레임별 파일 쓰기를 피하고 메모리에 모은 뒤 종료나 비활성 전환 시 내보낸다. 시작이나 처음 뜨는 효과의 긴 프레임은 예열 이후 결과와 함께 보존한다.

| 게임과 조건 | 기준과 관측 |

## Xcode Instruments 메모리 누수 감지와 기록

1. 기준·후보의 실행 파일과 자원, 소스 SHA와 dSYM UUID를 확인한다. 기기·OS·판본·화면·초기 시험 저장·시나리오·예열과 열 상태를 기록한다. 치트앱 스트레스, 정식 Release, 시뮬레이터를 겹치지 않게 실행한다.
2. 대상 프로세스에 **Allocations + Leaks**를 붙여 시작·안정 구간과 월드/메뉴·음향 중단/복귀를 반복한다. 같은 상태로 돌아왔을 때의 살아 있는 Heap/VM과 객체 수, 최고치와 반복 후 잔류량을 대조한다. Leaks에서 실제 완료한 검사 횟수와 검출 수를 기록한다. 필요하면 누수 객체·할당 스택과 소유 경로를 찾고 같은 반복으로 고친 결과를 확인한다.
3. `.trace`, 타깃/기간이 든 실행 명세, GUI의 Allocations·Leaks 관측, CLI export/TOC, JSON/CSV와 XCTest 결과를 같은 증거 폴더에 남긴다. 표를 내보내지 못하면 GUI에서 완료 검사와 결과를 직접 확인한다. 둘 다 근거가 없으면 미판정이다. 누적 할당량, 지속 할당, RSS, 누수 건수를 각각 기록한다. Time Profiler와 계측 없는 프레임 대조는 별도 실행으로 보존한다.
