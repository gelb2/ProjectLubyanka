# 정답지 작성과 판정 절차

## 모든 업무 지시의 착수 절차

1. 모든 지시·단순 질문·재개에서 프로젝트 지침이 지정한 공통·경로별 자아비판문 전문부터 읽는다. `lubyanka-oracle start <프로젝트> <새 작업 검토 파일>`은 빠진 양식을 생성하고 경로를 안내한다. 새로 만든 자아비판문도 전문을 읽는다.
2. 계획이나 코드를 쓰기 전에 최신 지시와 직접 관련된 정본문서를 찾는다. 사용자 요구, 보존 조건, 확인된 동작 또는 답변에 필요한 사실의 근거가 빠졌으면 기존 정본을 보강한다. 없으면 작성한다. 같은 범위의 정답지에도 요구별 출처·입력·기대값 또는 판정 규칙·필요한 증거를 작성하거나 반영한다. 루비얀카의 계획·답변 심사와 샤라시카의 시험에 같은 정답지를 사용한다. 미확정 판정은 명시하고, 해당 값에 의존하는 구현과 합격 판정을 미룬다.
3. 사용자 요구를 모두 포함한 개선책·대안과 실행·검증 계획을 세운다. 각 핵심 판단에서 자아비판문 원문과 그 적용 조건, 그 지적으로 달라진 조치나 검증, 해당 판단을 뒤집을 관측을 설명한다. 예를 들어 첫 행이 다음 착수를 막았다는 기록에 따라 첫 행만 지연시키고, 종료 전에 네 번째 행이 시작했는지 확인하는 시험을 계획한다. 총 소요 시간만 측정하는 안은 어떤 행이 막혔는지 드러내지 못한다.
4. 90% 기준은 원문의 내용이 계획의 핵심 선택·검증 방법을 실제로 뒷받침하는지로 심사한다. 핵심 선택의 근거가 부족하면 자아비판 실패다. 이전 계획을 폐기하고 전문을 처음부터 읽어 새 계획을 세운다. 새 지시나 문서·범위 변경도 전문 읽기부터 시작한다.

담당 AI가 정본문서와 정답지의 내용을 준비한다. `lubyanka`를 도입하면 독립 계획 검토와 Docker 시험, Git과 보고의 검증을 연결한다. [자동화 절차](managed.md)

## 샤라시카 필수 시험

1. **계획 완료 후.** 코드를 쓰기 전에 격리된 재현이나 작은 실험으로 계획의 가정, 필요한 입력, 관측 지점, 기대 결과와 기각 조건을 확인한다. 계획의 필수 시험이 모두 통과해야 개발을 시작한다.
2. **기능 구현 완료 후 커밋 전.** 커밋할 소스와 설정을 샌드박스에서 기능마다 최소 1회 실행한다. 해당 기능과 영향을 받는 경로의 정상, 정책의 허용·차단, 경계·복구를 검사한다. 시험 뒤 소스나 설정이 바뀌면 다시 실행한다.
3. **`dev` 병합 직전.** 최신 `dev`와 개발 브랜치를 결합한 정확한 후보를 시험한다. 모든 기능·코드 경로·정책을 정답지의 기대값과 연결한다. 정상, 경계, 실패와 복구를 검사한다. 같이 작동할 수 있는 기능은 자원·저장·상태를 공유하며 동시에 실행한다. 배타적인 상태는 나눠 각각 확인한다. 후보나 대상 브랜치가 바뀌면 다시 시험한다.
4. **어느 단계든 미통과면 자아비판 실패다.** 구현·커밋·병합을 멈추고 실행 원본과 기대·실제 결과를 남긴다. 전문을 처음부터 읽어 다시 계획하고, 외부 근거를 대조해 원인을 고친 뒤 필수 시험을 재실행한다. 실행할 수 없는 필수 시험은 미검증으로 남기고 통과를 보류한다.

샌드박스의 기능 시험에서는 화면이나 계정 정책으로 가려진 기능을 시험 빌드·계정·데이터에서 임시로 열어 제품 코드로 실행한다. 정책 시험에서는 원래 제약을 켜고, 허용된 경우와 차단할 경우를 각각 확인한다. 차단된 요청에 데이터·상태 변화가 있는지도 본다. 바꾼 접근 조건과 실행한 제품 경로를 기록하고 시험 자원과 운영 자원의 격리를 유지한다.

## 실행과 종료

1. 코드 작업은 기존 실패를 재현한다. 공식 명세·기술 문서 또는 검증된 공개 구현에서 베스트 프랙티스를 찾는다. 출처의 적용 조건과 현재 코드·사용자 요구를 대조해 기존 방식이 왜 실패하고 제안한 방식이 왜 실패를 막는지 논증한다. 논증한 뒤 코드를 고치고 같은 경로를 재실행한다.
2. 고칠 코드가 없어 보이면 이번 자아비판이 잘못됐다고 간주한다. 자아비판문 전문을 즉시 다시 읽고 놓친 코드와 가정을 외부 자료와 다른 입력 또는 관측으로 다시 검토한다. 후퇴를 발견한 경우에도 즉시 재독한다. 입증한 결함은 논증한 뒤 고친다. 확인할 수단이 남아 있으면 재독과 검토를 이어간다. 수단을 적용한 뒤에도 입증하지 못한 내용은 검토 범위와 남은 확인을 기록한다.
3. 종료 전에 두 정본을 개선한다. 정답지에는 사용자의 새 지시와 독립 근거가 바꾼 요구·판정·재현 조건을 반영한다. 자아비판문에는 놓친 가정, 외부 논증, 재현과 수정 결과를 반영한다. 후보가 만든 출력으로 기대값을 바꾸거나 미확인 실패를 사실로 적는 일은 금지한다.
4. 작업 검토 파일의 `review`에 적용한 지시 `instruction`과 남은 항목 `remaining`을 기록한다. `oracle`과 `selfCritique` 각각에 `status`, `summary`, `evidence`를 적는다. 파일을 고쳤으면 `updated`, 기존 내용을 유지했으면 `retained`를 쓴다. 변경 내용 또는 유지 이유와 확인한 코드·근거·실행 기록을 연결한다. 착수 기록인 `before`는 그대로 둔다.
5. 완료나 실패를 알리기 전에 작업 범위의 샤라시카 시험을 실제로 실행했는지 확인한다. 시험을 거치지 않은 종료는 업무 실패다. 보고를 멈추고 자아비판문 전문을 처음부터 읽어 새 계획으로 돌아간다. 코드가 없는 질문도 정답지의 원본과 실제 조건을 대조해 답변을 반증할 수 있는 검사를 한다.
6. 시험을 실행한 뒤 도입 프로젝트는 `lubyanka finish`로 샤라시카 기록과 검토를 대조한다. 스캐폴드만 쓰는 프로젝트는 `lubyanka-oracle finish <프로젝트> <작업 검토 파일>`로 문서 변경을 확인한다. 샤라시카 결과와 증거, 코드 검토 결과, 두 문서의 생성·수정·유지와 남은 확인을 사용자가 쓰던 CLI 또는 채팅에서 안내한다. 채팅 실행 환경은 `finish --json`과 샤라시카 실행 기록을 함께 읽는다.

`review.codeReview`에는 코드 검토 결과와 논증을 적는다. 지난 양식으로 시작한 작업도 같은 검토 파일에 이 항목을 추가할 수 있다.

| `result` | 함께 기록할 내용 |
| --- | --- |
| `fixed` | 외부 자료와 해당 절 `source`, 기존 코드와 수정안을 대조한 논증 `argument`, 수정 위치와 같은 경로의 재실행 결과 `verification`. 재독했다면 그 내용을 `reread`에 적는다. |
| `no-fix-found` | 전문 재독과 이전과 다른 입력 또는 관측 `reread`, 외부 자료 `source`, 대조 범위와 논증 `argument`, 재검토 결과 `verification`, 미입증 항목 `remaining`. CLI는 미입증 상태로 안내한다. |
| `pending` | 고치거나 재검토하는 중에 진행할 수 없게 된 이유 `argument`와 남은 확인 `remaining`. 확보한 근거와 재독 내용도 해당 필드에 적는다. |
| `not-applicable` | 소스코드 검토가 업무 범위에 없는 이유 `argument`. |

여러 작업이 두 정본을 동시에 수정할 때는 각 작업의 실제 diff를 대조한다. CLI는 검토 항목의 기입 여부와 문서의 파일 지문을 확인한다. `finish`의 종료 코드 `0`은 검토 기록을 출력했다는 뜻이다. 실제 전문 재독, 외부 출처의 적합성, 소스코드 수정 및 제품 판정은 원문과 실행 결과로 확인한다.

## 기본 JSON 정답지

1. `lubyanka-oracle.json`에 사용자 지시를 요구 한 건씩 옮긴다. `requirementId`는 중복 없이 고정한다. `source`에는 지시 원문이나 독립 근거의 경로·구절·판본 또는 확인 시점을 적는다.
2. `scope`에 확인 대상과 범위를 적고, `inputs`에 다른 사람이 같은 동작을 재현할 수 있도록 초기 상태·입력·순서·기기를 적는다.
3. `comparator`에서 정확 일치 `exact`, 범위 `range`, 불변 조건 `invariant`, 전후 관계 `relation`, 사람 검토 `manual` 중 하나를 고른다. `expectedOrRule`에 같은 값, 허용 조건, 검사 결과의 관계 또는 사람이 적용할 기준을 적는다. 기준이 없는 기대값은 `unresolved`에 남긴다.
4. `requiredEvidence`에는 실제로 확보할 관측을 적는다. 이전 실측이 있으면 `baseline`에 경로와 실측 조건을 적는다. 사용자 지시나 독립 자료에서 정한 기대값과 후보·이전 빌드의 관측을 따로 기록한다.
5. 프로젝트 폴더에서 `lubyanka-oracle check .`으로 필수 항목의 기입 상태를 확인한다. `start`에서 JSON 정답지를 `--oracle`로 지정했다면 `check`에도 같은 경로를 넘긴다. 실제 기능을 실행한 뒤 원본 증거를 대조해 요구별 통과·실패·미판정을 기록한다. 기준 또는 자료가 부족하면 해당 요구의 판정을 보류한다. 새 기준을 쓰게 되면 이유를 남기고 이전 결과와 후보를 같은 기준에서 비교한다.

채점 예시는 같은 요청을 두 번 보낸 뒤 저장 행이 하나인지 확인하는 것이다. 기대값은 사용자 계약에서 가져온다. 실제 응답 두 개와 저장소 재조회가 증거다. 기존 빌드가 두 행을 만든 기록은 고쳐야 할 기준선으로 보존한다.
